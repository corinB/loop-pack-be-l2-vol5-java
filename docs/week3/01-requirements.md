# 3주차 요구사항

## 기준과 상태

사용자가 제공한 Implementation Quest·Technical Writing Quest·Learning 자료와 최종 범위 합의를 기준으로 한다.
출발점은 corinB의 d30c06e이며, 현재 코드에서 주문 생성·확정 흐름을 읽어 확인했다.
아래는 구현 목표이며, 문서 작성만으로 기능·검사를 완료 처리하지 않는다.
원문 전체는 [필수 체크리스트](required-checklist.md), 구현 방식은 [트랜잭션 설계](02-transaction-design.md),
진행 순서는 [개발 계획](development-plan.md)을 따른다.

## 브랜드 삭제 계약

대상은 DELETE /api-admin/v1/brands/{brandId}이며 경로·성공 응답 형식은 유지한다.

- 기존 활성 상품 존재 시 409 거절을 **브랜드와 연결된 미삭제 상품 전체 처리 후 200 성공**으로 바꾼다.
- 기존 논리 삭제를 사용한다. 미삭제 상품은 재고가 0이어도 처리하고, 이미 삭제된 상품은 다시 변경하지 않는다.
- 상품이 하나도 없거나 모든 상품이 이미 삭제된 브랜드도 삭제할 수 있다.
- 없는 브랜드와 반복 삭제는 기존 404, 잘못된 ID 형식·범위는 기존 400으로 처리한다.
- 상품마다 delete()와 저장을 수행하고 브랜드까지 같은 트랜잭션으로 저장한다. 부분 성공·독립 commit은 없다.
- 고객 상품 목록·상세, 새 좋아요, 내 좋아요 목록, 새 주문에서 삭제 대상을 제외한다.
- 지정 사용자의 기존 좋아요 취소는 유지한다. 삭제된 상품의 수정·재고 변경은 기존 오류로 거절한다.
- 기존 관리자 조회의 활성 대상 필터도 유지한다. 별도의 삭제 대상 조회 API는 추가하지 않는다.
- 다른 브랜드·상품, 기존 Like 관계, Order·OrderItem·PointBill·OrderBill은 연쇄 삭제하지 않는다.
- 과거 주문의 상품명·수량·단가·총액·결제 결과는 저장된 값으로 조회하며 현재 가격으로 재계산하지 않는다.
- 삭제 전에 만든 DRAFT도 확정할 때 상품 존재·삭제 여부를 재검사하고 실패 시 전체 상태를 유지한다.

## 주문 생성·확정 계약

### 생성: POST /api/v1/orders

- 기존 201 응답과 DRAFT 상태, 상품명·단가·수량·금액 스냅샷 저장을 유지한다.
- 상품 존재·활성 여부, 양수 수량, 중복 품목 합산·계산 초과 검증은 유지한다.
- 재고·포인트의 가용량을 검사하거나 선점·차감하지 않는다. 생성 시 재고 잠금을 추가하지 않는다.
- 재고 1개에 서로 다른 DRAFT 여러 개를 생성할 수 있다. 실제 구매 가능 여부는 확정 시 결정한다.
- 주문 생성·GET 조회에 만료 시각·예약 수량·만료 상태·예약 관련 API 필드를 추가하지 않는다.

### 확정: POST /api/v1/orders/{orderId}/confirm

- 주문 → 상품 ID 오름차순 → 주문 사용자 포인트 순으로 잠근 뒤 보호된 데이터로 판단한다.
- 아직 DRAFT인지, 상품이 사용 가능한지, 각 품목 수량을 충족하는지, 잔액이 충분한지 검증한다.
- 결제액은 저장된 주문 합계다. 사용자 입력이나 현재 상품 가격으로 덮어쓰지 않는다.
- 재고·잔액 차감, PointBill(USE), OrderBill(PAID), CONFIRMED 변경을 하나의 트랜잭션에 반영한다.
- 성공은 기존 200과 결제 결과다. 없는 주문·상품은 기존 404, 삭제 상품도 기존 404로 처리한다.
- 재고 부족·잔액 부족·재확정은 기존 409와 메시지를 유지한다. 미확정 주문의 실패 시 DRAFT·기존 재고·잔액·기록을 보존한다.
- 재확정 실패에서는 이미 저장된 CONFIRMED와 기존 결제 결과를 그대로 유지한다.
- 잠금 시간 초과·교착·저장 오류는 업무 부족 오류로 바꾸지 않고 기존 500 처리와 오류 로그를 유지한다.
- 비관적 잠금의 자동 재시도는 추가하지 않는다. 기존 DB 잠금 대기 설정을 유지하고 실제 설정을 검증 기록에 남긴다.
- 잠금은 확정 처리 트랜잭션 종료 시 해제된다. DRAFT 생성부터 확정 요청까지 유지하는 잠금은 없다.

## 기존 사용자 입력과 공개 계약

X-USER-ID는 인증 정보가 아닌 fixture 사용자 입력이다.
필요 API의 누락·형식 오류 400, 없는 사용자 404를 유지한다.
주문 확정은 기존처럼 orderId를 받고 저장된 주문 userId로 결제한다.
관리자 기능에 사용자 헤더·권한 검사를 추가하지 않는다. 원문의 접근 제한을 구현했다고 기록하지 않는다.
기존 URL·응답 record·ApiResponse 형식은 유지하며 브랜드 삭제 거절 조건만 변경한다.

| T03 | 재고 5, 서로 다른 사용자·DRAFT 8개가 각각 1개 구매, 충분한 잔액 | 확정 5·재고 부족 3·기술 오류 0·재고 0 |
| T04 | 한 사용자 잔액 10,000원, 서로 다른 4,000원 DRAFT 3개, 충분한 재고 | 확정 2·잔액 부족 1·기술 오류 0·잔액 2,000원, 거절 주문의 재고 유지 |
| T05 | 잔액 10,000원에서 2,000원 충전과 7,000원 확정 동시 실행 | 두 요청 성공·기술 오류 0·잔액 5,000원 |
| T06 | 독립 트랜잭션 2개가 재고 5를 읽고 각각 상수 4 저장 | 성공 2·재고 4라는 불변식 위반을 assertion으로 확인 |
| T07 | 같은 주문 동시 확정, 역순 품목 주문, 관리자 재고 설정·차감 경쟁 | 추가 차감·중복 기록 없음, 잠금 순서 검증, 허용되는 직렬 실행 결과와 일치 |
| T08 | 생성·삭제 후 사용 제한·대표 HTTP·기존 회귀·정적 검사 | DRAFT 생성의 재고·포인트 불변, 입력·응답·저장 결과와 기존 계약 일치 |

- 초기 재고 − 성공 주문의 품목 수량 합 = 최종 재고.
- 초기 잔액 + 성공 충전액 합 − 성공 결제액 합 = 최종 잔액.
- 성공 + 업무 거절 + 기술 오류 = 전체 요청.
- 관리자 최종 수량 설정이 섞인 실험은 위 단순 재고 식 대신 실제로 가능한 직렬 처리 결과를 검증한다.
- 재고가 음수가 아니거나 HTTP 상태만 맞는 것으로 완료 처리하지 않는다.
- 실제 MySQL, 사전 commit, 독립 트랜잭션, 종료 후 별도 조회, 제한 시간과 자원 정리를 사용한다.
