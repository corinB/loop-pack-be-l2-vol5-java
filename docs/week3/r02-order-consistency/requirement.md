# R02. 주문·재고·포인트 정합성 보장

[전체 요구사항](../total_requirement.md) · 작업 브랜치: `volume-3/r02-order-consistency` · PR 대상: `volume-3/main`

상태: 요구사항 정리. R01 병합 후 상세 설계·구현·검증을 진행한다.
원문 대응: Implementation Quest 1의 주문·경쟁 흐름, 3, 4의 대조군·주문·경쟁 검증 및 Checklist 주문과 경쟁.
본인 주문 확인은 사용자 합의로 제외한다.

## 1. 목적

여러 품목의 주문 확정에서 재고·포인트·주문 상태·결제 결과가 함께 반영되거나 함께 취소되도록 한다.
동시에 같은 주문·재고·잔액을 변경하더라도 성공한 업무 결과와 최종 DB 상태가 일치해야 한다.
같은 행을 바꾸는 충전·관리자 재고 설정도 보호 규칙을 우회하지 않게 한다.

## 2. 현재 동작과 변경점

| 구분 | 현재 코드에서 확인한 동작 | 요구하는 변경 |
|---|---|---|
| 진입 API | `POST /api/v1/orders/{orderId}/confirm`, 요청 본문·사용자 헤더 없이 orderId 사용 | 기존 API 계약을 유지하며 최초 확정의 원자성·경쟁 제어 보완 |
| 업무 처리 | `ConfirmOrderService.execute`의 트랜잭션 안에서 도메인 상태·재고·포인트 검증 | 동시 요청에서도 보호된 최신 상태를 바탕으로 판단·변경 |
| 저장 | `ConfirmOrderWriter`가 기존 repository로 조회하고 JDBC로 재고·잔액·기록·주문 상태 저장 | 실제 조회·SQL과 같은 행의 다른 변경 경로에 일관된 보호 적용 |
| 기존 실패 테스트 | 재고·잔액 부족은 저장 호출 전 도메인 검증에서 실패 | 기존 검증을 유지하고 실제 변경 SQL 뒤 실패·전체 롤백을 추가 검증 |
| 동시 실행 | 2주차에서는 잠금·버전·재시도·동시 요청 검증 제외 | 재현용 대조군과 실제 서비스 경쟁 검증 추가 |

기존 트랜잭션 annotation이나 순차 재확정 거절만으로 동시 요청 안전성을 입증했다고 보지 않는다.

## 3. 포함·제외 범위

**포함**

- 최초 주문 확정의 정상·실패와 실제 저장 중 오류에 대한 전체 롤백.
- 주문 상태 검사·확정, 상품 사용 가능 여부·재고, 포인트 잔액의 보호와 일관된 처리 순서.
- 재고 경쟁·포인트 경쟁·충전과 결제, 같은 주문의 동시 확정, 관리자 최종 재고 설정과 주문 차감의 보호.
- 테스트 전용 갱신 유실 대조군, 실제 MySQL 서비스 통합 테스트, 대표 HTTP 연결·회귀 검사·설계 문서.

**제외**

- 인증·인가·본인 주문 확인 추가. 기존처럼 저장된 주문 사용자의 포인트를 사용한다.
- 주문 모델 재작성, 주문 취소·환불, 새 요청키·성공 응답 재사용 체계, 외부 결제.
- JVM 전역 `synchronized`, 제품 코드의 테스트용 장벽·sleep, 모든 잠금 후보의 추가 구현·비교 실험.
- 재고 요청 12개 실험, 브랜드 삭제와 상품 등록의 동시 실행. 브랜드 일괄 삭제 기능 자체는 R01의 책임이다.

## 4. 업무 규칙

1. 주문 생성은 DRAFT와 주문 당시 정보를 저장하며 재고·포인트를 차감하지 않는다.
2. 확정 시 DRAFT인지, 모든 상품을 사용할 수 있는지, 요청 총수량과 재고·잔액이 충분한지 확인한다.
3. 결제액은 저장된 주문 합계를 사용한다. 현재 상품 가격으로 과거 주문 금액을 다시 계산하지 않는다.
4. 재고·포인트 차감, USE 포인트 기록, 결제 기록, CONFIRMED 상태를 같은 DB 트랜잭션에서 반영한다.
5. 중간 오류·재고 부족·잔액 부족·삭제 상품 등으로 실패하면 부분 차감·추가 기록·확정 상태를 남기지 않는다.
6. 같은 주문의 상태 검사와 확정을 보호한다. 이미 CONFIRMED인 주문은 기존 상태 오류로 거절하며 추가 차감·결제 기록이 없어야 한다.
7. 비관적 잠금·낙관적 잠금·조건부 갱신 중 선택한 전략을 실제 repository·SQL에 적용한다. 방식은 후속 문답에서 결정한다.
8. 낙관적 충돌은 한정된 재시도로 현재 상태를 다시 판단한다. 실패한 트랜잭션을 종료하고 새 트랜잭션에서 재조회하며 횟수·대기 한도를 둔다.
9. 충돌 한도 초과·timeout·SQL 오류를 재고·잔액 부족으로 바꾸지 않는다. 필수 경쟁 사례에서는 기술 오류 없이 지정된 성공·거절 결과를 충족해야 한다.
10. 여러 상품은 일관된 식별자 순서로 처리한다. 주문·포인트·재고의 보호 순서는 다른 변경 경로와 맞춘다.
11. 충전·결제, 관리자 최종 재고 설정·주문 차감이 같은 행의 보호 규칙을 우회하지 않게 한다. repository/mapper의 저장 SQL도 확인한다.
12. 조회한 값을 판단하고 저장하는 실제 구간을 보호한다. 도메인 검증과 DB 경쟁 제어의 책임·실패 계약을 구분한다.

### 결과 대조식

- 초기 재고 − 성공 주문의 품목 수량 합 = 최종 재고.
- 초기 잔액 + 성공 충전액 합 − 성공 결제액 합 = 최종 잔액.
- 성공 + 업무 거절 + 기술 오류 = 전체 요청.

수량식은 관리자 최종 수량 설정이 섞이지 않은 주문 경쟁 사례에 적용한다.
관리자 설정과 주문 차감의 동시 실행은 절대 수량 설정이라는 기존 의미를 유지하며, 허용되는 순차 실행 결과와 대조한다.
응답뿐 아니라 DB의 주문·품목·포인트 및 결제 기록으로 성공량을 확인한다. 재고·잔액이 음수가 아닌지만 검사하지 않는다.

### 갱신 유실 대조군

제품 기능과 구분된 테스트 소스에서 아래 현상을 재현한다.

1. commit된 재고 5를 두 독립 트랜잭션이 잠금 없는 SELECT로 각각 읽는다. 최소 두 worker·connection을 확보한다.
2. 두 읽기 값이 모두 5임을 확인한 뒤 테스트 전용 post-read 장벽을 해제한다.
3. 각 트랜잭션은 읽은 값에서 1을 뺀 **상수 4**를 조건·version 없이 저장하고 commit한다.
4. 성공 2·최종 재고 4 및 `2 + 4 ≠ 5`를 assertion으로 확인해 갱신 유실을 설명한다.

`stock = stock - 1`로 대체하지 않는다. 두 번째 UPDATE의 변경 행 수 차이를 업무 실패로 세지 않는다.
timeout·SQL 오류를 재현 성공으로 간주하거나 의도적으로 실패하는 assertion을 방치하지 않는다.
대조군 통과를 제품 정합성 증거로 사용하지 않으며, 실제 서비스 검증에서는 worker 시작만 맞춘다.

- [ ] 실제 변경 SQL 뒤 실패를 유발하고 트랜잭션 종료 후 별도 DB 조회로 재고·잔액·주문·기록 전체 롤백을 확인했다.
- [ ] 선택한 제어가 실제 Spring 호출과 SQL에 적용되며, 프록시 진입점·예외·전파·잠금 순서를 기록했다.
- [ ] 같은 행을 변경하는 충전·결제·관리자 재고 설정·주문 차감 경로와 저장 SQL의 우회 가능성을 확인·보완했다.
- [ ] 재고 경쟁은 확정 5·재고 부족 3·재고 0, 포인트 경쟁은 확정 2·잔액 부족 1·잔액 2,000원을 충족했다.
- [ ] 충전과 결제는 모두 성공하며 잔액 5,000원을 충족했고, 위 세 경쟁 사례의 기술 오류는 모두 0건이다.
- [ ] 수량·잔액·요청 집계 대조식과 DB 주문·품목·기록이 일치하며, 거절 요청의 부분 반영이 없다.
- [ ] 갱신 유실 대조군을 실제 서비스 검증과 구분하고, 제한 시간·요청 결과 수집·자원 정리를 적용했다.
- [ ] 대표 성공·실패 HTTP 연결, R01의 삭제 후 확정 거절과 관련 브랜드·상품·포인트·주문 회귀를 확인했다.
- [ ] `./gradlew :apps:commerce-api:check`를 통과하고 Checkstyle·ArchUnit이 실제 변경 코드를 검사하는지 확인했다.
- [ ] AI 제안의 반례·변경 diff를 검토하고 `trade_off/`의 전체 목록·주제별 문서, `plan.md`, `result.md`에 선택·계획·실제 결과·한계·회고를 기록했다.

공통 MySQL·트랜잭션·worker 실행 규칙은 [전체 요구사항](../total_requirement.md)의 공통 검증 기준을 따른다.
실행한 테스트의 실제 이름·건수·실패·skip·종료 결과를 기록하며, 기존 코드만 읽고 검증 완료로 처리하지 않는다.

## 7. 미정 사항

아래 항목은 R01 병합 후 최신 코드에서 사용자와 비교·결정한다. 초기 문서에서는 구현 전략을 확정하지 않는다.

- 어떤 경쟁 제어 전략을 선택하고, 주문·포인트·상품 보호 범위와 순서를 어떻게 맞출 것인가?
- 기존 도메인 검증·JPA 조회·JDBC 일괄 저장 구조에서 선택한 제어를 어디에 적용할 것인가?
- 충전·관리자 재고 설정 및 같은 행의 다른 저장 경로에 필요한 최소 변경은 무엇인가?
- 충돌 재시도를 선택할 경우 새 트랜잭션 진입·횟수·대기 한도와 한도 초과 오류를 어떻게 표현할 것인가?
- 관리자 최종 수량 설정과 주문 차감의 테스트 데이터·허용 결과, 저장 후 실패 주입 경계, worker·connection 구성은 어떻게 정할 것인가?

위 선택은 작업 시작 시 만들 `trade_off/total_trade_off.md`와 주제별 문서, `plan.md`에 반영한다.
필수 성공·거절 수를 충돌 오류로 낮춰 잡거나 검사 기준을 완화하지 않는다.
