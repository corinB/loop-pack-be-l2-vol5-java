# 3주차 개발 계획

## 목표와 현재 작업 범위

목표는 브랜드 일괄 삭제·주문 확정의 원자성과 재고·포인트 동시성을 실제 MySQL로 검증하는 것이다.
기능·오류 기준은 [요구사항](01-requirements.md), 호출·저장·잠금·테스트 설계는
[트랜잭션 설계](02-transaction-design.md), 원문 대조는 [필수 체크리스트](required-checklist.md)를 따른다.

이번 실행은 **첫 브랜치 생성과 docs/week3 문서 작성·확인**을 다룬다.
후속 요청에 따라 문서를 작업 브랜치에 커밋하고 두 브랜치를 푸시한다. 기준 브랜치는 출발 커밋을 유지한다.
제품·테스트 코드 변경, 테스트 실행, PR 생성·병합은 수행하지 않는다.
아래의 기능 구현·테스트 실행 명령은 이후 작업 계획이며 현재 실행 결과가 아니다.

## 공통 작업 방식

1. 해당 요구사항의 정상 결과·대표 오류·실패 후 보존 상태를 확인한다.
2. 변경할 책임·파일 범위·관련 테스트를 밝힌 뒤 작은 기능 하나를 선택한다.
3. 핵심 규칙의 실패 테스트(Red) → 최소 구현(Green) → 리팩터링과 재검증을 수행한다.
4. diff를 확인하고 관련 테스트가 통과한 기능 단위로 커밋한다. 실패하는 상태를 커밋하지 않는다.
5. PR 완료 시 영향받는 회귀 테스트와 commerce-api check를 실행하고 실제 결과를 남긴다.
6. 사용자 승인을 받은 원격 작업으로 PR을 병합한 뒤 최소 회귀 검사를 확인하고 다음 브랜치를 만든다.

커밋 메시지는 기존의 type: 한글 요약 형식을 사용한다.
문서 변경만으로 기능·검사 완료 표시를 하지 않는다. 환경 문제·실패·skip은 그대로 기록한다.
Checkstyle·ArchUnit이나 기존 업무 규칙을 검사를 통과시키려고 약화시키지 않는다.
JUnit은 한글 DisplayName, 기능별 Nested, arrange·act·assert 구성을 따른다.
root AGENTS.md와 week2 컨벤션의 공통 구조·스타일·검사 규칙은 유지하되,
week2에만 해당하는 동시성 제외·브랜드 삭제 거절·브랜치 정책은 이 week3 계획으로 구분한다.
기존 Example과 무관한 패키지·사용자 변경은 수정하지 않는다.

## PR 01 — 설계·계획 정리

### 변경 책임

### 작업 순서

1. 시작 브랜치·커밋·사용자 변경을 확인하고 기준·작업 브랜치를 생성한다.

6. 문서 링크·충돌 문구·누락·diff를 확인하고 제품·테스트 코드 및 사용자 설정이 보존됐는지 확인한다.

후속 요청에 따라 위 문서 전체를 docs: 3주차 요구사항과 트랜잭션 개발 계획 정리 단위로 커밋한다.

## PR 03 — 주문 원자성·비관적 잠금

PointService·ProductService·브랜드 수정 경로 및 관련 테스트를 다룬다.

도메인에 Spring/JPA 의존을 추가하거나 모든 조회를 잠금 조회로 바꾸지 않는다.

관련 구현 커밋에는 그 기능의 통과 테스트를 함께 포함한다.

사용자별 포인트 데이터와 상품별 수량을 분리하여 검증하며 기술 오류를 업무 거절로 집계하지 않는다.
같은 JVM의 전역 synchronized, 운영 코드의 테스트 sleep·장벽·실패 API는 사용하지 않는다.

### 완료 조건

W3-R05~R08, T02~T07 및 T08의 주문·포인트 회귀를 확인한다.
다음 결과가 모두 성립해야 한다.

- 재고 경쟁: 확정 5·재고 부족 3·기술 오류 0·최종 재고 0.
- 포인트 경쟁: 확정 2·잔액 부족 1·기술 오류 0·최종 잔액 2,000원.
- 충전·결제 경쟁: 둘 다 성공·기술 오류 0·최종 잔액 5,000원.
- 실제 SQL 이후 실패: 전체 rollback, DRAFT와 기존 재고·잔액 보존, 신규 결제·사용 기록 없음.
- 재확정: 기존 성공 상태·기록을 유지하고 추가 차감 없음.
- JDBC·JPA가 실제로 같은 트랜잭션에 참여하고, 잠금 SQL과 정렬된 획득 순서가 확인됨.

잠금 대기·교착·SQL 오류는 자동 재시도 없이 기존 500·오류 로그로 처리한다.
상품 등록과 브랜드 삭제 동시 실행 등 제외한 시나리오를 검증 완료로 넓혀 쓰지 않는다.

## 테스트 실행과 결과 기록

수정 중에는 실제 작성한 관련 클래스부터 실행한다. 아래 신규 테스트명은 작성 예정 이름이다.

```powershell
.\gradlew.bat :apps:commerce-api:test --tests '*BrandRemovalTransactionTest'
.\gradlew.bat :apps:commerce-api:test --tests '*OrderTransactionTest'
.\gradlew.bat :apps:commerce-api:test --tests '*LostUpdateControlTest'
.\gradlew.bat :apps:commerce-api:test --tests '*OrderConcurrencyTest'
.\gradlew.bat :apps:commerce-api:check
```
