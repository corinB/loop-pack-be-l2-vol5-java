## 1. 기존 구현과 설계 유지·보완

- [ ] week2의 브랜드·상품·포인트·주문 API, repository, 테스트를 확장한다. 주문·재고 모델을 새로 만드는 과제가 아니다.
- [ ] 브랜드 일괄 처리, 최초 주문 확정, 같은 재고·잔액의 동시 변경을 설계 문서에 반영한다.
- [ ] 각 흐름의 트랜잭션 시작점·Controller부터 repository까지 호출 경로·예외·잠금 순서를 표시한다.
- [ ] 실제 Spring bean 프록시 경로, 자기 호출, 예외 삼키기, 독립 commit, 빠진 잠금 대상을 반례로 검토한다.
- [ ] 트랜잭션 경계와 선택한 동시성 전략의 이유를 기록하고 기존 계층·Context 책임과 작업 규칙을 유지한다.

## 2. 브랜드·연관 상품 일괄 삭제·비노출

대상 API: `DELETE /api-admin/v1/brands/{brandId}`.

- [ ] 활성 상품이 연결되면 거절하던 계약을 브랜드와 연결된 미삭제 상품 전체의 일괄 처리로 변경한다.
- [ ] 재고 0인 상품도 포함하며, 연결 상품이 없는 브랜드도 정상 처리한다.
- [ ] 없는 대상은 기존 없는 대상 오류를 반환한다.
- [ ] 브랜드와 상품의 모든 변경을 하나의 성공·실패로 묶고 부분 성공·상품별 독립 commit을 허용하지 않는다.
- [ ] 다른 브랜드·상품은 변경하지 않는다.
- [ ] 삭제 대상은 고객 목록·상세·새 좋아요·내 좋아요 목록·새 주문에서 제외한다.
- [ ] 지정 사용자의 기존 좋아요 취소는 유지하고, 삭제 대상 수정·재고 변경은 거절한다.
- [ ] 기존 주문의 품목·수량·단가·총액·포인트 결제 결과를 보존한다. 현재 가격으로 재계산하거나 주문을 연쇄 삭제하지 않는다.
- [ ] 삭제 전에 만든 DRAFT도 확정 시 상품 존재·삭제 여부를 재검사한다.
- [ ] 원문 기준으로 일반 사용자·식별 없는 관리자 요청을 거절하고 DB를 유지한다.

물리·논리 삭제는 선택 가능하나 기존 참조와 과거 주문을 보존해야 한다. cascade 설정만으로 업무 결과를 결정하지 않는다.

## 3. 주문 확정 원자성·동시성 제어

대상 API: `POST /api/v1/orders/{orderId}/confirm`.

- [ ] 주문 생성은 DRAFT 저장만 하고 재고·포인트를 차감하지 않는다.
- [ ] 원문 기준으로 본인 주문인지 확인하고 DRAFT 검사와 확정을 동시 요청으로부터 보호한다.
- [ ] 상품 사용 가능 여부·품목 총수량·재고·저장된 포인트 잔액을 확인한다.
- [ ] 재고·포인트 차감, CONFIRMED 변경, 결제액·결과 저장을 같은 DB 트랜잭션으로 처리한다.
- [ ] 중간 오류·재고 부족·잔액 부족 시 DRAFT와 기존 재고·잔액·결제 결과를 유지한다.
- [ ] 비관적 잠금·낙관적 잠금·조건부 갱신 중 선택한 전략을 실제 repository·SQL에 적용한다.
- [ ] 여러 상품은 일관된 ID 순서로 처리하고 주문·포인트·재고 보호 순서를 다른 변경 경로와 맞춘다.
- [ ] 포인트 충전·결제와 관리자 최종 재고 설정·주문 차감이 같은 보호 규칙을 준수한다.
- [ ] 이미 확정된 주문은 기존 상태 오류로 거절하고 추가 차감·결제 기록을 남기지 않는다.
- [ ] 낙관적 충돌을 재시도한다면 실패 트랜잭션 종료 후 새 트랜잭션에서 재조회·재판단하고 횟수·대기를 제한한다.
- [ ] 충돌 한도 초과·기술 오류를 재고 부족이나 잔액 부족으로 숨기지 않는다.
- [ ] 새 요청키·이전 성공 응답 재사용, 전역 synchronized, 실제 잠금 구간의 테스트 장벽·sleep을 추가하지 않는다.

## 4. 필수 재현·통합 테스트

### 갱신 유실 대조군

- [ ] 독립 트랜잭션 2개가 commit된 재고 5를 잠금 없이 읽고, 둘 다 5를 읽은 뒤 각각 상수 4를 저장한다.
- [ ] 조건·version 없는 갱신으로 성공 2·최종 재고 4를 재현하고, 불변식 위반이 재현됐다는 assertion을 통과시킨다.
- [ ] `stock = stock - 1` SQL로 대체하지 않고, 변경 행 수 차이를 업무 거절로 세지 않는다.
- [ ] 최소 worker·connection 2개와 제한 시간을 확보하고 timeout·SQL 오류를 재현 성공으로 처리하지 않는다.
- [ ] 읽기 이후 장벽은 이 대조군에만 사용한다.

### 실제 서비스 검증

| 시나리오 | 필수 준비·실행 | 기대 결과 |
|---|---|---|
| 브랜드 정상·실패 | 브랜드 1개와 상품 2개(하나는 재고 0), 다른 브랜드 상품, 과거 주문 | 정상은 대상 전체 제외, 중간 실패는 전체 복구, 다른 대상·과거 주문은 두 경우 모두 보존 |
| 주문 정상·실패 | 여러 품목의 DRAFT 확정, 실제 SQL 이후 다음 저장 단계 실패 | 정상은 전체 반영, 실패는 DRAFT·재고·잔액·결제 결과 모두 변경 전 상태 |
| 재고 경쟁 | 재고 5, 서로 다른 주문 8개가 1개씩 구매, 구매자별 충분한 잔액 | 확정 5·재고 부족 3·기술 오류 0·재고 0 |
| 포인트 경쟁 | 한 사용자 잔액 10,000원, 서로 다른 4,000원 주문 3개, 충분한 재고 | 확정 2·잔액 부족 1·기술 오류 0·잔액 2,000원, 거절된 주문의 재고 유지 |
| 충전·결제 경쟁 | 잔액 10,000원에서 2,000원 충전과 7,000원 결제 | 둘 다 성공·기술 오류 0·잔액 5,000원 |

- [ ] 요청 결과와 DB의 주문·품목·잔액을 함께 확인한다.
- [ ] 초기 재고 − 성공 주문 수량 합 = 최종 재고.
- [ ] 초기 잔액 + 성공 충전액 합 − 성공 결제액 합 = 최종 잔액.
- [ ] 성공 + 업무 거절 + 기술 오류 = 전체 요청.

### 테스트 실행 조건

- [ ] 기존 MySQL fixture를 사용하고 실제 application·repository 경로를 통과한다. mock·메모리 DB로 대체하지 않는다.
- [ ] 실제 변경 SQL 이후 테스트 구성의 다음 저장 경계에서 예외를 발생시켜 롤백을 검증한다.
- [ ] 서비스 트랜잭션 종료 후 별도 DB 조회로 확인하며 같은 JPA 관리 객체만 확인하지 않는다.
- [ ] worker 시작 전에 데이터를 commit하고 테스트 전체를 부모 트랜잭션으로 묶지 않는다.
- [ ] 실제 서비스 경쟁 테스트는 시작만 맞추고 요청마다 독립 트랜잭션을 사용한다.
- [ ] 모든 worker 종료 후 재조회하고 대기·future에 제한 시간을 둔다. finally에서 대기 해제·자원 정리를 수행한다.
- [ ] 브랜드 일괄 처리와 주문 확정의 대표 성공·실패를 HTTP에서도 확인한다.

## 5. 검사·문서·제출

- [ ] 관련 테스트의 실제 실행 건수·실패·종료 결과를 확인한다.
- [ ] 영향받는 브랜드·상품·포인트·주문 회귀 테스트와 기존 Checkstyle·ArchUnit을 실행한다.
- [ ] Java 모듈의 `./gradlew :apps:commerce-api:check`를 실행하고 실제 변경 코드가 검사 대상인지 확인한다.
- [ ] 로컬 실습 설정을 유지하고 공개 배포·실제 개인정보를 사용하지 않는다.
- [ ] 변경 코드·테스트·갱신 설계 문서·기술 글을 제출한다.
- [ ] PR에는 트랜잭션 경계·제어 전략·핵심 결과를 간결하게 기록한다.
- [ ] 기술 글은 한 주제를 자신의 코드·실험으로 설명하고 상황·개념·선택 이유·대안의 비용·미검증 한계를 담는다.

## 필수와 구분할 항목

**원문이 명시한 선택 확장:** 다른 잠금 전략 비교, 재고 요청 12개 실험, 브랜드 삭제와 상품 등록의 동시 실행.

**대화에서 논의했다가 철회한 확장:** 재고 선점·예약, DRAFT 10분 만료, 만료 재고 반환, Quartz·주기 작업·요청 시 예약 만료 처리.
이 항목들은 원문 필수가 아니며 최종 합의에 따라 이번 구현 범위에서도 제외했다.
특히 주문 생성부터 재고를 예약하면 원문의 DRAFT 8개 확정 경쟁과 계약이 달라진다.
원문 필수 테스트를 이 확장 테스트로 대체하지 않는다.

**학습 범위 합의:** 사용자는 이번에도 인증·인가·본인 여부 검사를 제외하기로 했다.
이는 원문의 접근 경계 요구를 충족했다는 의미가 아니라, 원문에서 의도적으로 제외한 범위다.
