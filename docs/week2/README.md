## 기준 자료

- 초기 `base` 초안 4개를 참고해 설계를 정리했다. 현재 작업 폴더에는 원본이 없어 초기 자료로만 기록한다.
- 첨부 `Implementation Quest`: 2주차 필수 기능·HTTP 경로·접근 제어·검증 조건의 기준이다.
- [도메인 모델 그림](img/Loop_Model.png), [이벤트 스토밍 그림](img/Loop_Event.png): 네 Context와 업무 흐름의 참고 자료다.
- 이번 대화에서 승인한 계획: 원본의 미정 정책을 결정한 근거다.

**과제 요구**와 **합의한 선택**은 [정책 문서](02-business-policies.md)에서 구분한다.
설계·도메인 모델링·TDD 학습에 집중하기 위해 원문의 인증·인가 요구는 이번 범위에서 제외했다.
동시성 구현·검증은 다음 학습으로 미룬다. 순차 재확정 거절·DB 유일성 제약·단일 요청의 전체 롤백은 유지한다.
X-USER-ID는 학습용 사용자 입력이며 권한·본인 여부를 검증하지 않는다. 적용 API는 [API 계약](05-use-cases.md)을 따른다.
문서 작성만으로 과제의 구현·설정·검사 항목을 완료 처리하지 않는다. 원격 제출은 별도 요청에 따른다.

## 핵심 결정

| 주제 | 결정 |
|---|---|
| 실행 구조 | 단일 서버·DB, Mall / Shopping / Ordering / Pay |
| 주문 상태 | DRAFT → CONFIRMED |
| 주문 확정 | 재고·포인트·이력·결제·주문 상태를 하나의 트랜잭션으로 저장 |
| 실패 | 부분 저장 없이 전체 롤백 |
| 개발 순서 | volume-2/main을 기준으로 총 7개 PR, 계획 정리는 PR 01에 포함 |
| 조회 | 좋아요 관계의 10초 주기 DB 집계, 현재 상품 정보와 주문 스냅샷 구분 |
| 삭제 | 논리 삭제, 기존 주문 정보 보존 |
| 이벤트 | 업무 사실을 표현하며 비동기 메시지 처리를 요구하지 않음 |
| 코드 구조 | 순수 domain / JPA Entity 분리, 계층 → Context → 기능 |
| 실행·조회 | 쓰기 UseCase + Service, GET QueryController → QueryDao → JdbcClient |
| 변환·테스트 | 전용 EntityMapper, 핵심 도메인 규칙의 TDD·엄격한 경계 검증 |

## 원본에서 구체화한 부분

`CREATED` 상태와 취소·환불 예시는 이번 범위에서 사용하지 않는다.
포인트·주문 조회는 선택 기능이 아니라 필수 기능이다.
Aggregate는 규칙의 경계이며, 이번 주문 확정 트랜잭션은 여러 Aggregate를 함께 변경한다.
이는 원본의 “1 Transaction = 1 Aggregate” 제안 대신 선택한 방식이다.
