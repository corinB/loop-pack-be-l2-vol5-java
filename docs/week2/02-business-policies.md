# 비즈니스 정책

**과제**는 첨부 자료의 확정 요구, **합의**는 이번 대화에서 승인한 설계 선택이다.
오류 응답은 [Error Specification](07-error-specification.md)을 따른다.
원문의 인증·인가 조건은 설계·도메인 모델링·TDD 학습 범위에 맞춰 제외했다. 아래 최신 합의를 적용한다.

## 입력과 식별

| ID | 정책 | 근거 |
|---|---|---|
| P01 | 좋아요 등록·취소, 포인트 충전·잔액, 주문 생성·목록은 X-USER-ID로 사용자를 지정 | 학습 범위 합의 |
| P02 | 필요한 사용자 입력의 누락·형식 오류 400, 없는 사용자 404; 본인 여부 검사 없음 | 학습 범위 합의 |
| P03 | 관리자 경로는 기능 구분용; 사용자 헤더·ADMIN 역할·CSRF 검사 없음 | 학습 범위 합의 |
| P04 | 브랜드·상품 이름은 앞뒤 공백 제거 후 1~100자, 중복 허용 | 합의 |
| P05 | 설명은 선택, 최대 1,000자 | 합의 |
| P06 | 상품 가격·충전액·결제액은 1 이상의 정수, 잔액은 0 이상 | 과제 + 합의 |
| P07 | 금액은 long 범위, 수량·재고는 int 범위; 덧셈·곱셈 초과 거절 | 합의 |
| P08 | 주문 수량은 양수, 최종 재고는 0 이상; 누락·잘못된 타입 거절 | 과제 |

금액의 최대 표현값은 `9,223,372,036,854,775,807`, 수량·재고는 `2,147,483,647`이다.
JSON 숫자 필드는 정수로 받으며 소수·문자열·null을 정수로 보정하지 않는다.
필수 ID는 양의 정수이며 long 범위다. 잘못된 입력은 400이다. X-USER-ID는 인증 정보가 아닌 학습용 입력이다.
좋아요 목록은 경로 userId로 조회하며 헤더와 비교하지 않는다. 주문 상세·확정은 orderId를 사용한다.
결제 대상은 주문에 저장된 userId다. 상품·브랜드 조회도 사용자 헤더를 요구하지 않는다.
헤더를 사용하지 않는 API는 전달된 헤더를 무시한다. 사용자 ID를 요청 본문에 추가하지 않는다.

## 상품·브랜드·좋아요

| ID | 정책 | 근거 |
|---|---|---|
| P09 | 상품 등록은 활성 브랜드만 참조, 정보 수정으로 브랜드 변경 불가 | 과제 |
| P10 | 재고 변경은 증감량이 아닌 최종 수량 설정 | 과제 |
| P11 | 브랜드·상품은 논리 삭제, 삭제 대상 재수정·재고 변경 불가 | 과제 + 합의 |
| P12 | 재고가 0이어도 활성 상품이 연결된 브랜드는 삭제 불가 | 과제 |
| P13 | 고객·관리자 모두 활성 브랜드·상품만 조회, 반복 삭제는 404 | 합의 |
| P14 | 동일 사용자–상품 좋아요 관계는 최대 하나 | 과제 |
| P15 | 반복 좋아요 등록·없는 관계 취소는 성공, 중복 저장·음수 집계 없음 | 합의 |
| P16 | 삭제 상품은 새 좋아요·사용자별 목록에서 제외, 지정 사용자의 기존 관계 취소 가능 | 과제 + 학습 범위 합의 |
| P17 | 좋아요 수는 관계 COUNT를 주기적으로 저장한 집계 값 사용; 관계·내 목록은 즉시 반영 | 과제 + 반영 시점 합의 |

좋아요 등록은 상품 유효성 검사를 먼저 한다. 삭제 상품은 기존 관계가 있어도 등록 요청을 404로 거절한다.
취소는 헤더로 지정한 사용자의 관계만 제거하며 상품의 활성 여부를 전제하지 않는다. 관계가 없어도 성공한다.
상품 논리 삭제는 Like·OrderItem을 연쇄 삭제하지 않는다. 품절 상품의 조회·좋아요는 허용한다.

상품별 집계는 Shopping이 소유한다. 모든 상품 응답의 likeCount와 likes_desc 정렬은 같은 저장 집계 값을 사용한다.
내 좋아요 목록의 포함 여부는 즉시 반영하지만 각 상품의 likeCount는 집계 시점의 값이다.
단일 commerce-api 인스턴스에서 시작 시 한 번, 이전 집계 종료 10초 후 다시 실행한다. 반영 지연에는 실행 시간도 포함된다.
미집계 상품은 0을 표시하며, 마지막 좋아요가 취소된 상품의 기존 집계도 0으로 갱신한다.
전체 갱신은 하나의 트랜잭션이다. 실패하면 이전 값을 유지하고 로그를 남긴 뒤 다음 정기 실행에서 다시 시도한다.
별도 즉시 재시도·Redis·메시징·다중 인스턴스 조율은 이번 범위에 포함하지 않는다.

## 포인트·주문

| ID | 정책 | 근거 |
|---|---|---|
| P18 | 1포인트 = 1원, 충전은 잔액에 더하고 저장된 잔액 반환 | 과제 |
| P19 | fixture 사용자마다 초기 잔액 0의 Point를 준비 | 실습 기본값 |
| P20 | 주문은 한 품목 이상, 같은 상품은 수량 합산 후 저장 | 과제 + 합의 |
| P21 | 생성 시 활성 상품·양수 수량 확인, 상품명·단가를 스냅샷으로 저장 | 과제 + 합의 |
| P22 | 생성은 DRAFT 저장만 수행; 재고 검사·예약·재고 및 포인트 차감 없음 | 합의 |
| P23 | 지정한 주문이 DRAFT인지 확인, 상품 활성 여부·수량·현재 재고·주문 사용자 잔액 재검사 | 과제 + 학습 범위 합의 |
| P24 | 확정 결제액은 저장된 주문 합계; 현재 상품 가격으로 재계산하지 않음 | 합의 |
| P25 | 재고 → 포인트·기록 → 주문 확정을 하나의 트랜잭션으로 처리 | 합의 |
| P26 | 어느 단계든 실패하면 전체 롤백; 실패 기록도 별도로 남기지 않음 | 합의 |
| P27 | 재확정은 409, 같은 주문의 성공 결제는 한 번만 저장 | 합의 |

품목 금액은 `unitPrice × quantity`, 주문 합계는 품목 금액의 합이다.
중복 합산 전 각 수량을 검증하고, 합산 수량·품목 금액·총액·충전 후 잔액의 범위 초과를 거절한다.
PointBill은 충전·사용 내역, OrderBill은 성공한 주문 결제 내역이다. 외부 결제는 없다.

P19의 fixture는 PR 01에서 최소 User·두 사용자를 준비하고 PR 04에서 초기 잔액 0의 Point를 연결한다.
fixture 연결 시 기존 잔액은 초기화하지 않는다.
P27의 재확정 거절은 순차 요청으로 검증하며 DB 유일성 제약과 단일 요청의 전체 롤백은 유지한다.
동시성 구현·검증(잠금·버전 검증·재시도·동시 요청 테스트)은 다음 학습으로 미룬다.

## 조회

| ID | 정책 | 근거 |
|---|---|---|
| P28 | 목록 기본값 page=0, size=20; page ≥ 0, 1 ≤ size ≤ 100 | 합의 |
| P29 | 상품 기본 정렬 latest, price_asc·likes_desc 지원; 동률은 ID 내림차순 | 과제 + 합의 |
| P30 | 나머지 목록은 생성 시각 내림차순, 동률은 해당 항목 ID 내림차순 | 합의 |
| P31 | 잘못된 페이지·정렬·필터 형식은 400; 없는·삭제된 브랜드 필터는 빈 목록 | 합의 |

내 좋아요 목록의 생성 시각은 관계 등록 시각이며 동률에는 productId를 사용한다.
빈 결과와 범위를 벗어난 페이지는 200과 빈 items를 반환한다.

## 선택 이유

| 선택 | 비교한 대안 | 선택 이유 |
|---|---|---|
| 단일 트랜잭션 | Context별 저장·보상 | 단일 DB에서 부분 실패를 간단히 방지 |
| 논리 삭제·주문 스냅샷 | 물리 삭제·현재 상품 참조 | 과거 주문과 기존 참조 보존 |
| DB 주기 재집계 | 조회마다 COUNT·Redis·이벤트 처리 | 표시 지연을 허용하고 원본 관계에서 집계를 복구하는 흐름 학습 |
| 좋아요 반복 성공 | 반복 요청 오류 | 원하는 관계 상태로 수렴, 주문은 별도로 재확정 거절 |

위 정책은 승인된 기준이다. 범위를 넓히거나 정책을 바꿀 때는 영향과 질문을 먼저 기록하고 확인한다.
