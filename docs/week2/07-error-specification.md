# Error Specification

실패 응답과 **실패 후 저장 상태**를 함께 정의한다.
아래 E번호는 문서·테스트의 추적 ID이며 API의 errorCode 문자열과는 다르다.

## 오류 계약

| ID | HTTP / errorCode | 발생 조건 | 유지할 상태 |
|---|---|---|---|
| E01 | 400 / Bad Request | 필수값 누락, 타입·범위·이름·수량·페이지·정렬 오류 | 기존 값 유지, 신규 데이터 없음 |
| E02 | 400 / Bad Request | 헤더가 필요한 API의 X-USER-ID 누락·형식·범위 오류 | 모든 업무 변경 없음 |
| E04 | 404 / Not Found | 없는 사용자·주문, 없는·삭제된 브랜드/상품, 반복 논리 삭제 | 기존 값·관계 유지 |
| E05 | 409 / Conflict | 활성 상품이 연결된 브랜드 삭제 | 브랜드·상품 삭제 상태 유지 |
| E06 | 409 / Conflict | 주문 확정 시 하나 이상의 상품 재고 부족 | 모든 재고·잔액·DRAFT·기록 유지 |
| E07 | 409 / Conflict | 주문 확정 시 포인트 부족 | 모든 재고·잔액·DRAFT·기록 유지 |
| E08 | 409 / Conflict | 이미 CONFIRMED인 주문 재확정 | 추가 차감·기록 없음, 기존 결제 결과 유지 |
| E09 | 400 / Bad Request | 충전 후 잔액·중복 합산 수량·품목 금액·총액 계산 초과 | 잔액 유지 또는 주문 생성 없음 |
| E11 | 500 / Internal Server Error | 예상하지 못한 저장·서버 오류 | 해당 트랜잭션 전체 롤백 |

errorCode는 기존 ErrorType의 HTTP reason phrase 형식을 유지한다.
인증·인가를 제외한 학습 범위이므로 401·403 오류와 관련 테스트는 구현하지 않는다.
이전 접근 제어용 E03·E10은 범위 제외로 폐기하며 다른 오류의 추적 ID는 유지한다.
동일 HTTP 코드의 업무 오류는 message로 설명한다. E번호를 응답 필드에 새로 추가하지 않는다.

신규 domain은 HTTP를 모르는 `DomainException`과 `DomainErrorCode`를 사용한다.
사용자·상품·주문 존재 여부 등의 application 오류도 HTTP 상태 없이 표현하고, interfaces에서 이 표의 응답으로 변환한다.
예를 들어 내부 `INSUFFICIENT_STOCK`은 E06의 `409 / Conflict`로 매핑한다.
기존 ErrorType·CoreException을 신규 domain에 가져오지 않으며 내부 코드 추가로 공개 errorCode를 바꾸지 않는다.

## 응답 예

```json
{
  "meta": {
    "result": "FAIL",
    "errorCode": "Conflict",
    "message": "포인트가 부족합니다."
  },
  "data": null
}
```

| 오류 | 대표 message |
|---|---|
| 입력 오류 | 충전 금액은 양의 정수여야 합니다. |
| 사용자 헤더 입력 오류 | X-USER-ID는 양의 정수여야 합니다. |
| 사용자 없음 | 사용자를 찾을 수 없습니다. |
| 상품 없음 | 상품을 찾을 수 없습니다. |
| 브랜드 삭제 충돌 | 활성 상품이 연결된 브랜드는 삭제할 수 없습니다. |
| 재고 부족 | 상품 재고가 부족합니다. |
| 재확정 | 이미 확정된 주문입니다. |
| 계산 범위 초과 | 계산 결과가 허용 범위를 초과했습니다. |

메시지 예시는 오류 의미를 설명하며 오류 코드보다 세부 문구에 의존하는 클라이언트 로직은 피한다.
고객·관리자용 HTTP 테스트는 입력·응답 봉투·저장 결과를 검증한다. 보안 필터를 추가하지 않는다.

## 검사 흐름과 예외

필요한 사용자 입력·존재 여부와 업무 규칙을 검사하며 본인 여부는 검사하지 않는다.
주문 확정은 존재 여부 → DRAFT → 상품 활성 여부·재고 → 저장된 주문 사용자의 잔액 순서로 검사한다.
역직렬화 단계에서 거절될 수 있으므로 여러 오류가 섞인 입력에 대한 전역 우선순위는 보장하지 않는다.

| 상황 | 처리 |
|---|---|
| 올바른 형식의 없는 브랜드 필터 | 오류 대신 200 빈 상품 목록 |
| 이미 등록된 활성 상품 좋아요 | 오류 대신 200, 기존 관계 유지 |
| 삭제·없는 상품에 대한 좋아요 취소 | 존재하는 헤더 사용자의 관계만 제거, 없으면 그대로 200 |
| 좋아요 목록의 경로·헤더 userId 불일치 | 헤더를 무시하고 경로 사용자를 조회 |
| 주문 확정에 다른 사용자 헤더 전달 | 헤더를 무시하고 주문 사용자 포인트로 결제 |
| 삭제된 상품에 대한 좋아요 등록 | 기존 관계가 있어도 E04 |
| 주문 생성 당시보다 상품 가격이 바뀜 | 오류 아님, 저장된 가격으로 확정 |
| DRAFT 상품이 삭제됨 | 확정 E04, 주문·재고·잔액 그대로 |

## 실패 후 상태 검증

| 시나리오 | 재조회하여 확인할 값 |
|---|---|
| 재고 5개, 6개 주문 확정 | 재고 5개, 잔액 동일, DRAFT, 결제·USE 기록 없음 |
| 두 품목 중 두 번째 재고 부족 | 첫 번째를 포함한 모든 재고·잔액 동일 |
| 재고 충분·잔액 부족 | 재고 차감 롤백, 잔액 동일, DRAFT, 새 결제·USE 기록 없음 |
| 충전 0·음수·소수·문자열·표현 범위 초과 | 기존 잔액, CHARGE 기록 수 동일 |
| long 최대 잔액에 1 충전 | E09, 잔액이 음수로 바뀌지 않음 |
| 중복 수량 합산 또는 금액 곱셈 초과 | E09, Order·OrderItem 생성 없음 |
| 재확정·브랜드 삭제 거절 | 값뿐 아니라 관계·기록 개수도 동일 |
| 필요한 헤더 누락·형식 오류 또는 없는 사용자 | 각각 400·404, 값·관계·기록 변화 없음 |

저장 통합 테스트는 flush/clear 후 재조회하고, HTTP 테스트는 실제 저장 상태도 확인한다.
전체 API와의 연결은 [Use Case](05-use-cases.md), 값 범위는 [정책](02-business-policies.md)을 따른다.
