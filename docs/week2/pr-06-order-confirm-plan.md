# PR 06 구현 계획: 주문 확정·롤백

> 이 문서는 PR06을 담당하는 개발자를 위한 작업 지침을 겸한다. 아래 "선행 조건"을 반드시 먼저 읽어달라.

## 선행 조건 (중요 — 반드시 확인)

- `docs/week2/development-plan.md`의 PR 순서는 **PR04 → PR05 → PR06 → PR07**로, PR06은 PR05가 만드는 `Order`/`OrderItem` 도메인과 `OrderBill` 저장 구조 위에서 주문 확정 로직을 구현하도록 설계되어 있다. 이번 확인 시점(2026-09-18) 기준 `domain/ordering`은 빈 디렉토리이고, `Order`/`OrderItem`/`OrderBill` 코드는 아직 어디에도 없다.
- 사용자(PM/리드) 확인 결과, 이번에는 **PR05·PR06 브랜치를 모두 지금의 `volume-2/main`에서 독립적으로 분기**했다([pr-05-order-create-query-plan.md](pr-05-order-create-query-plan.md)도 동일한 시점의 `main`에서 분기됨). 즉 이 브랜치에는 아직 `Order` 도메인이 없다.
- **실제 주문 확정 코드 작성에 착수하기 전에** 다음을 확인해야 한다:
  1. PR05가 어느 정도 진행됐는지(머지됐는지, 아니면 브랜치에 `Order`/`OrderItem`/`OrderBill` 구현이 올라와 있는지) 확인한다.
  2. 이 브랜치를 PR05 브랜치(또는 병합된 `main`) 기준으로 리베이스할지, 아니면 다른 방식으로 `Order` 도메인을 가져올지는 **임의로 정하지 말고 사용자에게 먼저 확인한다.**
- 위 확인 전까지는 이 문서의 범위·요구사항 정리 수준에서 작업하고, `Order` 도메인을 전제로 하는 실제 코드(ConfirmOrderUseCase 등)는 작성하지 않는다.

## 목표

PR06은 고객이 지정한 DRAFT 주문을 확정한다: 상품 재고·주문 사용자의 포인트를 차감하고, `USE` 타입 `PointBill`과 `OrderBill`을 기록한 뒤 주문을 `CONFIRMED`로 전환한다. 모든 처리는 하나의 트랜잭션으로 묶이며, 어느 단계든 실패하면 전체 롤백한다.
브랜치는 `volume-2/pr-06-order-confirm`, 기준은 `volume-2/main`(PR04 병합 시점, 위 "선행 조건" 참고)이다.
관련 요구사항은 [01-requirements.md](01-requirements.md)의 R08(전체), R09·R13(확정 이후 상세·결제 결과 조회 검증 부분), 업무 규칙은 [02-business-policies.md](02-business-policies.md)의 P23~P27, 계약은 [05-use-cases.md](05-use-cases.md)를 따른다.

**이 문서는 범위·요구사항·완료 조건을 정리하는 단계이며, 아직 실제 코드는 없다.** 클래스·패키지 단위의 세부 설계는 위 선행 조건이 해소되고 구현에 착수할 때 확정한다.

## 작업 방식 (이번 세션·이 PR 전반에 적용)

- **선택적 테스트 실행**: 구현 중에는 변경과 직접 관련된 테스트 클래스만 `--tests`로 먼저 실행해 빠르게 반복하고, 논리적 커밋 직전마다 `./gradlew :apps:commerce-api:check` 전체(Checkstyle·ArchUnit·전체 테스트)를 실행해 회귀가 없는지 확인한다. 빌드 인프라의 태그 분리(@Tag 등)는 별도 결정 없이 도입하지 않는다.
- **애매하거나 중요한 결정은 추론하지 않고 질문**: 요구사항·업무 정책·기존 코드 어디에도 명시되지 않은 부분이거나 여러 해석이 가능한 설계 선택은 임의로 정하지 말고 사용자에게 먼저 확인한다. 특히 위 "선행 조건"의 브랜치 베이스 전략은 반드시 확인 후 진행한다. `docs/week2/conventions.md` 8절에도 동일한 원칙이 명시되어 있다.

## 범위

### 주문 확정

- 요구사항 R08: 지정한 DRAFT에서 재고·주문 사용자 포인트를 차감하고 결제 결과를 저장한다.
- 업무 규칙(P23~P27):
  - P23: 지정한 주문이 DRAFT인지 확인하고, 상품 활성 여부·수량·현재 재고·주문 사용자 잔액을 재검사한다.
  - P24: 확정 결제액은 저장된 주문 합계를 사용하며, 현재 상품 가격으로 재계산하지 않는다.
  - P25: 재고 차감 → 포인트 차감·기록 → 주문 확정을 하나의 트랜잭션으로 처리한다.
  - P26: 어느 단계든 실패하면 전체 롤백하며, 실패 기록은 별도로 남기지 않는다.
  - P27: 재확정은 409로 거절하고, 같은 주문의 성공 결제는 한 번만 저장한다.
- API: `POST /api/v1/orders/{orderId}/confirm` — 경로 `orderId`, 본문 없음 → 200 OrderDetail. 오류 E04(주문 없음/DRAFT 상품 삭제), E06(409, 재고 부족), E07(409, 포인트 잔액 부족), E08(409, 이미 CONFIRMED인 주문 재확정).
- 저장 경계(04-domain-model.md): 확정 한 번의 트랜잭션에 모든 대상 Product 재고, Point, `USE` PointBill, OrderBill, Order 상태 변경이 함께 들어간다.
