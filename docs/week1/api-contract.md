# 주문 할인 외부 API 계약

[대표 문서](order-discount-contract.md) · [요구사항](requirements.md) · [규칙](invariants.md) · [설계 결정](design-decisions.md)

과제에서 지정한 API 형태와 응답 항목에 사용자 검토를 거친 설계를 기록한다. 미작성 항목과 정책의 답이 미확인인 항목은 문답으로 보완한다.

## 기본 API

`POST /api/v1/orders/{orderId}/discount`

| 항목 | 작성 내용 |
|---|---|
| 연결할 사용 흐름 | UC-001 — 주문에 쿠폰 적용 |
| 사용자 식별 방식 | 서버가 검증한 로그인 정보에서 요청자의 사용자 ID를 얻는다. 사용자 검토 후 선택한 설계이며 제품 담당자의 답변으로 간주하지 않는다. |
| 식별 정보의 신뢰 근거 | 요청 본문에 적힌 사용자 ID만으로 요청자의 신원을 믿지 않는다. 서버가 검증한 로그인 정보를 근거로 식별한다. 세션·토큰 등 구체적인 인증 방식은 아직 정하지 않았다. |
| 호출 권한과 관련 제품 질문 | INV-001에 따라 요청자 ID와 쿠폰 보유자 ID를 비교해 구매자가 보유한 쿠폰인지 확인한다. 그 밖의 호출 권한은 미작성이다. |

요청 본문에는 적용할 `couponId`를 보낸다. 요청자 식별을 위해 본문의 `userId`를 신뢰하는 방식은 선택하지 않는다.

## 입력

| 항목 | 위치 | 자료형·형식 | 필수 여부 | 검증 조건 | 근거 |
|---|---|---|---|---|---|
| orderId | 경로 | 양의 정수 | 필수 | 숫자가 아님·0·음수·소수는 형식 오류. 존재 여부는 별도 확인 | 과제 지정 경로·학습자가 선택한 입력 설계 |
| couponId | JSON 본문 | 양의 정수 | 필수 | 누락·null·숫자가 아님·0·음수·소수는 형식 오류. 존재 여부는 별도 확인 | 과제 지정 요청 정보·학습자가 선택한 입력 설계 |

요청 예시 — 100번 주문에 200번 쿠폰 적용 요청:

```http
POST /api/v1/orders/100/discount
Content-Type: application/json

{"couponId": 200}
```

양의 정수라는 형식과 실제 대상의 존재 여부를 구분한다. 구체적인 정수 상한은 아직 정하지 않았다.

## 성공 조건과 응답

| 항목 | 작성 내용 |
|---|---|
| 성공으로 보는 조건 | 쿠폰 적용 조건을 충족하고 계산 결과가 규칙에 맞아야 한다. 다만 결과 저장까지 완료해야 성공인지, 예상 금액만 계산해도 성공인지는 미확인이다. |
| 성공 시 보장할 저장 상태 | 미확인 — P-001/Q2의 답이 필요하다. 응답 정보가 정해졌다는 이유만으로 저장 완료를 보장한다고 정하지 않는다. |
| HTTP status | `200 OK` — 성공 결과를 응답 본문으로 전달한다. 성공의 저장 보장 여부는 여전히 미확인이다. |
| meta.result | `SUCCESS` |
| data 유무와 구조 | `data` 객체에 `orderId`·`originalAmount`·`discountAmount`·`finalAmount`를 담는다. |
| 연결할 요구·규칙 | UC-001의 적용 가능 여부 확인·할인 계산·결과 전달 흐름, INV-001~006의 적용 조건과 계산·결과 처리 규칙. 저장 보장 여부는 P-001/Q2와 연결한다. 미확인 정책과 재요청 분기는 관련 질문의 답을 받은 뒤 보완한다. |

아래는 과제에서 요구한 응답 정보에 대해 사용자와 합의한 의미다. 필드명과 주문 ID의 양의 정수 형식은 사용자 검토 후 선택했다. 금액은 설명용 예시만 원 단위를 사용하며 실제 통화·자료형·소수 처리·허용 범위는 미확인이다.

| 응답 정보 | 필드명 | 자료형·단위 | 의미·기준 시점 | 예시 값 | 근거 |
|---|---|---|---|---|---|
| 주문 ID | `orderId` | 양의 정수 | 쿠폰 적용을 요청한 주문의 식별자 | 100 | 과제 지정 응답 정보·사용자 검토 |
| 원금 | `originalAmount` | 미확인 — 예시만 원 단위 | 쿠폰 할인 전 주문 금액 | 10,000원 | 과제 지정 응답 정보·사용자 검토 |
| 할인 금액 | `discountAmount` | 미확인 — 예시만 원 단위 | 이번 적용 결과에서 차감하는 금액 | 1,000원 | 과제 지정 응답 정보·사용자 검토 |
| 최종 금액 | `finalAmount` | 미확인 — 예시만 원 단위 | 원금에서 할인 금액을 뺀 금액 | 9,000원 | A-002·INV-003 |

이 응답을 받았다는 사실만으로 주문이나 할인 금액이 확정됐다고 보지 않는다. 확정 시점과 결과 저장 여부는 P-001/Q1~Q2·P-002/Q1의 답이 미확인이다.

성공 응답 예시 — HTTP `200 OK`:

```json
{
  "meta": {"result": "SUCCESS"},
  "data": {
    "orderId": 100,
    "originalAmount": 10000,
    "discountAmount": 1000,
    "finalAmount": 9000
  }
}
```

금액 10,000 − 1,000 = 9,000은 설명용 값이다. 위 JSON의 숫자 표기로 실제 금액 자료형을 확정하지 않는다. 성공 시 오류 필드의 포함 여부는 미정이며, 예시는 합의한 `meta.result`와 `data`만 보여준다. 적용 조건을 충족한 성공 사례를 가정했으며 결과 저장이나 주문 확정을 보장한다는 뜻은 아니다.

## 오류 계약

실패 응답은 `meta.result`를 `FAIL`로 표시하고, `meta.errorCode`와 `meta.message`에 오류 코드와 안내 문구를 담으며, `data`는 `null`로 둔다. 이는 사용자와 선택한 계약이며 실제 API 관찰 결과가 아니다.

오류가 뜻하는 상황과 호출자의 다음 행동을 함께 작성한다. 제품 질문의 답이 필요하면 확정하지 않고 미확인으로 남긴다.

| 오류 상황 | 관련 요구·규칙 | HTTP status | meta.result | error code | data 유무 | 요청자의 다음 행동 | 실패 후 상태 | 정책 확인 상태 |
|---|---|---|---|---|---|---|---|---|
| 구매자 A가 구매자 B의 쿠폰 적용을 요청한다. | P-001·INV-001 | `403 Forbidden` | `FAIL` | `COUPON_NOT_APPLICABLE` | `null` | 본인이 보유한 쿠폰을 선택해 다시 요청한다. | 해당 쿠폰을 적용하지 않는다. | 소유권 규칙은 제품 약속에 근거한다. 아래 안내 방식은 사용자 검토 후 선택한 설계다. |
| 입력 형식 오류 | 학습자가 선택한 입력 설계·UC-001 | 400 | `FAIL` | `INVALID_REQUEST` | `null` | 입력 수정 후 재요청 | 해당 요청의 쿠폰 적용을 수행하지 않는다. | 학습자가 선택한 설계 |
| 존재하지 않는 주문 | 학습자가 선택한 존재 여부 오류 설계·UC-001 | 404 | `FAIL` | `ORDER_NOT_FOUND` | `null` | 주문 확인·재선택 | 해당 요청의 쿠폰 적용을 수행하지 않는다. | 학습자가 선택한 설계 |
| 존재하지 않는 쿠폰 | 학습자가 선택한 존재 여부 오류 설계·UC-001 | 404 | `FAIL` | `COUPON_NOT_FOUND` | `null` | 쿠폰 확인·재선택 | 해당 요청의 쿠폰 적용을 수행하지 않는다. | 학습자가 선택한 설계 |
| 확정된 주문에 신규 적용 | P-001 | 409 | `FAIL` | `ORDER_ALREADY_CONFIRMED` | `null` | 해당 주문의 신규 적용 시도를 중단 | 요청한 쿠폰을 새로 적용하지 않는다. | 재요청은 별도 미확인 |

### 확정된 주문의 신규 적용 오류

| 항목 | 합의한 내용 |
|---|---|
| 실패 상황 | 주문 확정 후 쿠폰을 신규 적용하려고 한다. |
| 근거 | P-001 — 주문 확정 전에 쿠폰을 적용할 수 있다. |
| 응답의 의미 | 현재 주문 상태에서는 신규 적용할 수 없다. |
| 안내 문구 | “확정된 주문에는 쿠폰을 새로 적용할 수 없습니다.” |
| 요청자의 다음 행동 | 해당 주문에 대한 신규 적용 시도를 중단한다. |
| 처리 결과 | 요청한 쿠폰을 새로 적용하지 않는다. |
| 응답 형식 | `meta.result`는 `FAIL`, `meta.errorCode`는 `ORDER_ALREADY_CONFIRMED`, `meta.message`는 위 안내 문구, `data`는 `null`이다. HTTP status는 `409 Conflict`다. 현재 주문 상태와 요청한 신규 적용 작업이 충돌하기 때문이다. |

이미 성공한 동일 요청을 다시 보내는 경우는 이 신규 적용 오류로 확정하지 않는다. 해당 경우는 [규칙 문서의 충돌 검토](invariants.md)의 P-001·INV-005 질문으로 남겨두며 답변은 미확인이다.

### 쿠폰 소유권 오류의 외부 의미

| 항목 | 합의한 내용 |
|---|---|
| 응답의 의미 | 요청한 쿠폰을 사용할 권한이 없다. |
| 안내 문구 | “사용할 수 없는 쿠폰입니다.” |
| 제공할 정보의 범위 | 다른 사람의 쿠폰이라는 세부 정보 대신 사용할 수 없다는 안내를 제공한다. |

오류 코드는 `COUPON_NOT_APPLICABLE`로 정했다. 보유 여부를 직접 드러내는 `COUPON_NOT_OWNED` 대신 사용 불가를 알리는 이름을 선택했다. 이 코드를 만료·교체 등 미확인 상황에도 사용한다고 정하지 않는다. HTTP 상태 코드는 `403 Forbidden`으로 정했다. 요청한 쿠폰을 사용할 권한이 없기 때문이다.

### 미확인 · 만료된 쿠폰의 적용 요청

| 항목 | 합의한 내용 |
|---|---|
| 상황 | 요청 시작 시각이 만료 시각을 지난 쿠폰을 적용하려 한다. |
| 판단 가능한 것 | 해당 쿠폰은 만료 상태다. |
| 미확인 | 요청을 어떻게 처리하고 어떤 결과를 반환할지 |
| 연결 질문 | A-004/Q2 — 만료된 쿠폰을 주문에 적용하려고 하면 어떻게 처리하나요? |
| 답변 후 정할 것 | 응답의 의미·안내 문구·요청자의 다음 행동·처리 후 상태 |

만료 여부를 판별하는 규칙과 만료된 요청을 처리하는 정책을 구분한다. 이 항목을 확정된 오류 계약으로 간주하지 않는다.

### 미확인 · 다른 쿠폰으로 교체 요청

| 항목 | 합의한 내용 |
|---|---|
| 상황 | 확정 전 주문에 쿠폰 A가 적용된 상태에서 B를 요청한다. |
| 정해진 조건 | A-001·INV-002에 따라 한 주문에 두 쿠폰을 동시에 적용할 수 없다. |
| 미확인 | A를 B로 교체할지, B 요청을 거절할지 |
| 연결 질문 | P-001/Q3 — 다른 쿠폰으로 교체할 수 있나요? |
| 답변 후 정할 것 | 성공·실패 응답과 기존 쿠폰·할인 금액의 처리 |

한 장만 적용한다는 조건만으로 교체 불가를 결정하지 않는다. 이 항목을 확정된 오류 계약으로 간주하지 않는다.

오류 응답 예시 — 모두 학습자가 선택한 설계이며 실제 HTTP 관찰 결과가 아니다.

HTTP 400

```json
{
  "meta": {
    "result": "FAIL",
    "errorCode": "INVALID_REQUEST",
    "message": "요청 정보를 확인해 주세요."
  },
  "data": null
}
```

HTTP 404

```json
{
  "meta": {
    "result": "FAIL",
    "errorCode": "ORDER_NOT_FOUND",
    "message": "존재하지 않는 주문입니다."
  },
  "data": null
}
```

HTTP 404

```json
{
  "meta": {
    "result": "FAIL",
    "errorCode": "COUPON_NOT_FOUND",
    "message": "존재하지 않는 쿠폰입니다."
  },
  "data": null
}
```

HTTP 403

```json
{
  "meta": {
    "result": "FAIL",
    "errorCode": "COUPON_NOT_APPLICABLE",
    "message": "사용할 수 없는 쿠폰입니다."
  },
  "data": null
}
```

HTTP 409

```json
{
  "meta": {
    "result": "FAIL",
    "errorCode": "ORDER_ALREADY_CONFIRMED",
    "message": "확정된 주문에는 쿠폰을 새로 적용할 수 없습니다."
  },
  "data": null
}
```

여러 오류가 동시에 해당하는 경우의 검사 우선순위는 정하지 않는다. 위 오류들은 각 상황을 따로 설명하며, 기존 미확인 정책을 확정하지 않는다.


## 재요청과 조건 충돌

| 항목 | 작성 내용 |
|---|---|
| 같은 요청을 구분할 기준과 근거 | 미확인 — A-003/Q1. 주문 ID와 쿠폰 ID가 같다는 이유만으로 같은 요청이라고 정하지 않는다. |
| 재요청 시 반환할 결과 | A-003·INV-005에 따라 같은 요청의 결과를 재사용한다. 실패 결과도 재사용하는지는 A-003/Q2의 미확인 사항이다. |
| 재요청과 다른 조건이 겹칠 때의 판단 | 할인 정책이 바뀐 경우는 A-003/Q3에 연결한다. 쿠폰 만료·주문 확정 후의 재요청은 [규칙 문서의 충돌 검토](invariants.md)에 연결하며 처리 우선순위는 미확인이다. |
| 관련 제품 질문과 답변 상태 | A-003/Q1~Q3 및 기존 만료·주문 확정 후 재요청 충돌 검토 질문. 정책 답변은 미확인이다. |

설명용으로 처음 결과가 할인 금액 1,000원·최종 금액 9,000원이었다면, 같은 요청으로 판단되고 결과 재사용 대상이라면 그 결과를 다시 반환한다. 이 예시로 같은 요청의 기준이나 재사용 대상을 확정하지 않는다.

## 기본 형태와의 차이

현재 합의한 method·path·요청 필드·성공 응답 정보는 과제 지정 형태와 차이가 없다. `POST /api/v1/orders/{orderId}/discount`를 유지한다. 금액 표현과 정수 상한 등 미확정 항목은 별도로 남긴다.

선택 이유: 과제에서 지정한 API 형태를 사용한다. 상태 코드의 일반적인 의미는 [HTTP 표준 RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-15)에 근거하며, 각 오류에 상태 코드를 연결한 것은 사용자와 선택한 설계다. 실제 API 관찰 결과가 아니다.

- [ ] 각 응답의 근거를 요구·사용 흐름·규칙에서 찾을 수 있다.
- [ ] 오류별 요청자의 다음 행동과 실패 후 상태를 기록했다.
- [ ] 미확인 정책을 확정된 API 동작으로 쓰지 않았다.
- [ ] 호출자가 알아야 할 정보와 내부에서 처리할 내용을 구분했다.
