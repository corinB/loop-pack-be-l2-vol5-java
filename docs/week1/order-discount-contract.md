모호한 쿠폰 요구에서 출발해, 확인된 약속과 아직 답이 없는 질문을 나누고 API와 내부 책임까지 연결한 문서다. 다음 구현자는 각 결정의 근거와 미확인 사항을 함께 읽어야 한다. 기존 분할 문서는 상세 학습 기록으로 유지한다.

## 1. 목적·출처·범위

> 구매자는 주문 확정 전에 보유 쿠폰을 적용할 수 있고, 확정된 할인 금액은 나중에 바뀌지 않아야 합니다.

이 문서에서 **제품 약속**, **실습 조건**, **학습자가 선택한 설계**는 서로 다른 출처다. 질문을 선택했다고 정책의 답까지 확인된 것은 아니다. `미확인`은 답이 없는 정책, `미정·미작성`은 아직 정하지 않은 설계 항목을 뜻한다.

출처 없는 추가 정책 제안은 사용자 확인 결과 **해당 없음**이다. 설명용 숫자와 가상 사례는 실제 제품 정책으로 취급하지 않는다.

## 2. 제품 약속과 실습 조건

제품 약속은 보장해야 할 결과이고, 실습 조건은 이번 과제의 범위를 좁히기 위해 주어진 입력이다.

### 확인된 제품 약속

| ID | 과제 원문 |
|---|---|
| P-001 | 구매자는 주문 확정 전에 보유 쿠폰을 적용할 수 있다. |
| P-002 | 확정된 할인 금액은 이후에도 유지된다. |

### 실습용 전제

실제 제품 정책으로 확정된 조건이 아니라, 이번 과제의 설계 범위를 좁히기 위한 입력이다.

| ID | 과제 원문 |
|---|---|
| A-001 | 한 주문에는 쿠폰 한 장만 적용한다. |
| A-002 | `finalAmount = originalAmount - discountAmount`로 계산한다. |
| A-003 | 같은 요청의 결과를 재사용한다. |
| A-004 | 쿠폰 만료 여부는 요청 시작 시각을 기준으로 판단한다. |

### UC-001 · 주문에 쿠폰 적용

사용자가 검토한 쿠폰 적용 유스 케이스다. 세부 흐름과 상태는 후속 단계에서 필요한 만큼 구체화한다.

| 항목 | 내용 |
|---|---|
| ID | UC-001 |
| 이름 | 주문에 쿠폰 적용 |
| 액터 | 구매자 |
| 목적 | 주문에 할인을 적용하고 할인 후 금액을 확인한다. |
| 시작 사건 | 구매자가 주문과 쿠폰을 선택해 적용을 요청한다. |
| 기본 조건 | 주문 확정 전이며, 구매자가 보유한 쿠폰이어야 한다. |
| 기본 흐름 | 적용 가능 여부 확인 → 할인 금액·최종 금액 계산 → 적용 결과 전달 |
| 성공 결과 | 구매자가 적용 결과와 금액을 확인한다. |
| 실패 결과 | 구매자에게 적용하지 못한 이유를 알려준다. |
| 처리 후 저장 상태 | 미확인. 결과 저장 여부에 대한 답변이 필요하다. |
| 미확정 분기 | 교체·취소·만료 처리와 같은 요청의 구체적인 판단 기준 |

기본 조건은 P-001 제품 약속에 근거한다. 만료나 금액 제한의 구체적인 처리 방식은 답변을 받은 뒤 보완한다. 성공·실패 후 저장 상태나 세부 분기를 이 표만으로 확정하지 않는다.

## 5. 규칙 6개와 반례

각 규칙은 어떤 약속에서 나왔는지, 어떤 상황에서 깨지는지, 누가 지킬지를 함께 읽는다. 반례의 가정으로 미확인 정책을 확정하지 않는다.

### INV-001 · 소유권

| 항목 | 작성 내용 |
|---|---|
| 출처 구분·관련 조건/질문 | 제품 약속 P-001 — 구매자는 보유 쿠폰을 적용할 수 있다. |
| 규칙 내용 | 적용하는 쿠폰은 요청한 구매자가 보유한 쿠폰이어야 한다. |
| 정책 확인 상태 | 제품 약속에 근거한 규칙으로 사용자 검토 후 기록 |
| 깨지는 입력·상태·실행 순서 | 구매자 A가 구매자 B의 쿠폰을 적용하려고 한다. |
| 기대 결과·남는 상태·외부 응답 | 해당 쿠폰을 적용하지 않고, 적용할 수 없음을 구매자에게 알린다. |
| 책임 후보·선택 이유 | 쿠폰 사용 가능 여부를 확인하는 부분. 요청자와 쿠폰 보유자를 비교해 사용 가능 여부를 판단해야 하기 때문이다. |

구체적인 클래스 이름은 미정이다. 오류 코드는 후속 API 설계에서 `COUPON_NOT_APPLICABLE`로 선택했다.

### INV-002 · 쿠폰 개수

| 항목 | 작성 내용 |
|---|---|
| 출처 구분·관련 조건/질문 | 실습 전제 A-001 — 한 주문에는 쿠폰 한 장만 적용한다. |
| 규칙 내용 | 한 주문에 두 장 이상의 쿠폰이 동시에 적용되어서는 안 된다. |
| 정책 확인 상태 | 이번 과제의 실습 전제로 주어졌으며 실제 제품 정책으로 확정된 것은 아니다. |
| 깨지는 입력·상태·실행 순서 | 쿠폰 A가 적용된 주문에 B도 추가해, 두 쿠폰의 할인이 함께 반영된다. |
| 기대 결과·남는 상태·외부 응답 | 두 쿠폰이 동시에 적용된 상태를 만들지 않는다. |
| 책임 후보·선택 이유 | 주문의 쿠폰 적용 상태를 관리하는 부분. 주문에 현재 적용된 쿠폰을 확인하고 개수를 제한해야 하기 때문이다. |

B 요청을 거절할지, A를 B로 교체할지는 P-001/Q3의 미확인 정책이다. 이 규칙으로 확정할 수 있는 것은 두 장의 동시 적용을 허용하지 않는다는 점이다.

### INV-003 · 금액 관계와 경계

| 항목 | 작성 내용 |
|---|---|
| 출처 구분·관련 조건/질문 | 실습 전제 A-002 — `finalAmount = originalAmount - discountAmount`로 계산한다. |
| 규칙 내용 | `최종 금액 = 원금 − 할인 금액`을 만족해야 한다. |
| 정책 확인 상태 | 계산식은 이번 과제의 실습 전제다. 원금·할인 금액·최종 금액의 허용 범위는 미확인이다. |
| 깨지는 입력·상태·실행 순서 | 원금 10,000원, 할인 금액 1,000원인데 최종 금액이 8,000원으로 나온다. |
| 기대 결과·남는 상태·외부 응답 | 계산식에 맞는 최종 금액은 9,000원이다. 계산식과 다른 결과를 정상적인 할인 결과로 처리하지 않는다. |
| 책임 후보·선택 이유 | 할인 금액과 최종 금액을 계산하는 부분. 계산한 금액들이 주어진 계산식을 만족하도록 보장해야 하기 때문이다. |

원금·할인 금액·최종 금액의 최솟값과 최댓값은 A-002/Q1~Q3의 답을 받은 뒤 보완한다.

### INV-004 · 확정 결과 보존

| 항목 | 작성 내용 |
|---|---|
| 출처 구분·관련 조건/질문 | 제품 약속 P-002 — 확정된 할인 금액은 이후에도 유지된다. |
| 규칙 내용 | 할인 금액이 확정되면, 이후에도 그 금액을 유지해야 한다. |
| 정책 확인 상태 | 확정된 할인 금액 유지는 제품 약속이다. 할인 금액의 확정 시점은 P-002/Q1의 미확인 사항이다. |
| 깨지는 입력·상태·실행 순서 | 할인 금액을 1,000원으로 확정했는데, 쿠폰 정책이 바뀌었다는 이유로 2,000원으로 변경한다. |
| 기대 결과·남는 상태·외부 응답 | 기존에 확정된 할인 금액 1,000원을 유지한다. |
| 책임 후보·선택 이유 | 확정된 할인 결과를 관리하는 부분. 이후 변경이 발생해도 확정된 할인 금액을 보존해야 하기 때문이다. |

할인 금액이 언제 확정되는지는 P-002/Q1의 답을 받은 뒤 보완한다. 확정된 결과의 보존 방식은 DEC-002에서 snapshot으로 선택했으며 저장 시점과 세부 저장 항목은 미정이다.

### INV-005 · 같은 요청의 결과 재사용

| 항목 | 작성 내용 |
|---|---|
| 출처 구분·관련 조건/질문 | 실습 전제 A-003 — 같은 요청의 결과를 재사용한다. |
| 규칙 내용 | 같은 요청이 다시 들어오면 이전 처리 결과를 재사용해야 한다. |
| 정책 확인 상태 | 결과 재사용은 이번 과제의 실습 전제다. 같은 요청의 구체적인 기준과 실패 결과의 재사용 여부는 A-003/Q1~Q2의 미확인 사항이다. |
| 깨지는 입력·상태·실행 순서 | 같은 요청으로 판단된 재요청인데, 처음에는 할인 금액 1,000원을 반환하고 다음에는 새로 계산한 2,000원을 반환한다. |
| 기대 결과·남는 상태·외부 응답 | 처음 처리한 결과인 할인 금액 1,000원을 다시 반환한다. |
| 책임 후보·선택 이유 | 요청 식별과 이전 결과 재사용을 조정하는 부분. 같은 요청인지 판단하고, 해당 요청의 이전 결과를 찾아 연결해야 하기 때문이다. |

반례는 동일한 요청이라고 판단된 상황을 가정한다. 같은 요청의 구체적인 기준과 실패 결과의 재사용 여부를 이 반례로 확정하지 않는다.

### INV-006 · 만료 판단과 경계

| 항목 | 작성 내용 |
|---|---|
| 출처 구분·관련 조건/질문 | 실습 전제 A-004 — 쿠폰 만료 여부는 요청 시작 시각을 기준으로 판단한다. |
| 규칙 내용 | 쿠폰 만료 여부를 요청 시작 시각과 만료 시각을 비교해 판단한다. |
| 정책 확인 상태 | 요청 시작 시각 기준은 이번 과제의 실습 전제다. 요청 시작 시각과 만료 시각이 정확히 같은 경우의 처리는 A-004/Q1의 미확인 사항이다. |
| 깨지는 입력·상태·실행 순서 | 만료 시각은 12:00:00이고 요청은 11:59:59에 시작했는데, 처리 시각이 12:00:01이라는 이유로 만료라고 판단한다. |
| 기대 결과·남는 상태·외부 응답 | 요청 시작 시각을 기준으로 만료 전이라고 판단한다. |
| 책임 후보·선택 이유 | 쿠폰 사용 가능 여부를 확인하는 부분. 요청 시작 시각과 쿠폰 만료 시각을 비교해 만료 여부를 판단해야 하기 때문이다. |

만료 전이라는 판단이 곧 적용 성공을 뜻하지는 않는다. 다른 적용 조건도 충족해야 한다. 요청 시작 시각과 만료 시각이 정확히 같은 경우는 A-004/Q1의 답을 받은 뒤 보완한다.

## 6. 경계와 충돌 검토

계산식이 맞는 것과 허용되는 금액인 것은 다르다. 또한 재요청의 결과 재사용과 다른 제한이 겹칠 때는 적용 범위를 확인해야 한다.

### 추가 검토 · 금액 경계

| 검토 항목 | 현재 판단 | 연결 질문·조건 |
|---|---|---|
| 원금의 최솟값·최댓값 | 미확인 | A-002/Q3 |
| 할인 금액의 최솟값·최댓값 | 미확인 | A-002/Q1 |
| 최종 금액의 최솟값·최댓값 | 미확인 | A-002/Q2 |
| 계산식 | `최종 금액 = 원금 − 할인 금액` | 확인된 실습 조건 A-002 |

설명용 입력인 원금 10,000원 − 할인 금액 12,000원 = 최종 금액 −2,000원은 계산식에는 맞는다. 그러나 허용되는 금액인지는 아직 판단할 수 없다. 음수 금액을 거절하거나 0원으로 보정하는 처리도 임의로 정하지 않는다. 이 예시는 계산식의 충족과 금액 범위의 허용 여부를 구분하기 위한 것이며, 음수 금액을 허용한다는 정책이 아니다.

### 추가 검토 · 할인 한도 변경

| 항목 | 검토 내용 |
|---|---|
| 가상 상황 | 할인 금액 5,000원이 확정된 후, 최대 할인 한도가 3,000원으로 변경된다. |
| 확인된 약속 | P-002: 확정된 할인 금액은 이후에도 유지된다. |
| 규칙이 깨지는 처리 | 새 한도에 맞춰 기존의 확정된 할인 금액을 3,000원으로 변경한다. |
| 기대 결과 | 이미 확정된 할인 금액 5,000원을 유지한다. |
| 관련 규칙 | INV-004 — 확정 결과 보존 |

할인 한도의 존재와 금액은 설명용 가정이며 실제 정책으로 확정한 것이 아니다. 실제 금액 제한은 A-002/Q1~Q3의 미확인 사항이지만, 확정된 할인 금액의 보존은 확인된 제품 약속이다.

### 추가 검토 · 만료 시각 경계

만료 시각을 `12:00:00`으로 둔 설명용 사례다.

| 요청 시작 시각 | 만료 여부 판단 |
|---|---|
| 11:59:59 | 만료 전 |
| 12:00:00 | 미확인 — A-004/Q1의 답 필요 |
| 12:00:01 | 만료 후 |

만료 여부는 요청 시작 시각으로 판단하되, 정확히 같은 순간을 만료에 포함하는지는 미확인이다. 만료됐을 때 어떤 응답을 보낼지는 A-004/Q2의 답이 필요하다. 만료 후라고 판단할 수 있어도 구체적인 실패 응답까지 정해진 것은 아니다.

### 재요청과 조건의 충돌 가능성

| 관련 규칙 | 충돌할 수 있는 상황 | 결정할 우선순위·범위 | 연결할 제품 질문 | 상태 |
|---|---|---|---|---|
| INV-005 · INV-006 | 쿠폰 적용에 성공한 뒤 쿠폰이 만료됐고, 같은 요청이 다시 들어온다. | 재요청에도 만료 판단을 다시 수행하는지, 그 판단이 이전 결과 반환에 영향을 주는지 미확인 | 이전에 성공한 요청을 다시 보냈을 때 쿠폰이 만료되어 있다면, 기존 성공 결과를 그대로 반환하나요? (관련: A-003/Q1, A-004/Q2~Q3) | 검토 질문 기록, 정책 답변 미확인 |
| P-001 · INV-005 | 쿠폰 적용에 성공한 뒤 주문이 확정됐고, 같은 요청이 다시 들어온다. | 주문 확정 전이라는 적용 제한이 이미 처리된 결과의 반환에도 적용되는지 미확인 | 이미 성공한 요청을 주문 확정 후 다시 보내면, 기존 성공 결과를 반환하나요? 아니면 주문이 확정됐다는 이유로 거절하나요? (관련: P-001/Q1, A-003/Q1) | 검토 질문 기록, 정책 답변 미확인 |

약속과 규칙의 적용 범위와 우선순위를 확인하기 위한 사례다. 두 사례 모두 같은 요청으로 판별됐다고 전제한다. 실제로 규칙이 모순된다고 확정한 것은 아니며, 만료되거나 주문이 확정됐다는 이유만으로 재요청을 실패 처리한다고 정하지 않는다.

## 7. 외부 API 계약

UC-001을 외부에서 요청하는 방법과 결과의 의미를 정의한다. 아래 형식과 오류 코드는 학습자가 선택한 설계이며, 실제 API를 호출해 관찰한 결과가 아니다.

### 기본 API

`POST /api/v1/orders/{orderId}/discount`

| 항목 | 작성 내용 |
|---|---|
| 연결할 사용 흐름 | UC-001 — 주문에 쿠폰 적용 |
| 사용자 식별 방식 | 서버가 검증한 로그인 정보에서 요청자의 사용자 ID를 얻는다. 사용자 검토 후 선택한 설계이며 제품 담당자의 답변으로 간주하지 않는다. |
| 식별 정보의 신뢰 근거 | 요청 본문에 적힌 사용자 ID만으로 요청자의 신원을 믿지 않는다. 서버가 검증한 로그인 정보를 근거로 식별한다. 세션·토큰 등 구체적인 인증 방식은 아직 정하지 않았다. |
| 호출 권한과 관련 제품 질문 | INV-001에 따라 요청자 ID와 쿠폰 보유자 ID를 비교해 구매자가 보유한 쿠폰인지 확인한다. 그 밖의 호출 권한은 미작성이다. |

요청 본문에는 적용할 `couponId`를 보낸다. 요청자 식별을 위해 본문의 `userId`를 신뢰하는 방식은 선택하지 않는다.

### 입력

| 항목 | 위치 | 자료형·형식 | 필수 여부 | 검증 조건 | 근거 |
|---|---|---|---|---|---|
| orderId | 경로 | 양의 정수 | 필수 | 숫자가 아님·0·음수·소수는 형식 오류. 존재 여부는 별도 확인 | 과제 지정 경로·학습자가 선택한 입력 설계 |
| couponId | JSON 본문 | 양의 정수 | 필수 | 누락·null·숫자가 아님·0·음수·소수는 형식 오류. 존재 여부는 별도 확인 | 과제 지정 요청 정보·학습자가 선택한 입력 설계 |

요청 예시 — 100번 주문에 200번 쿠폰 적용 요청:

```http
POST /api/v1/orders/100/discount
Content-Type: application/json

{"couponId": 200}
```

양의 정수라는 형식과 실제 대상의 존재 여부를 구분한다. 구체적인 정수 상한은 아직 정하지 않았다.

### 성공 조건과 응답

| 항목 | 작성 내용 |
|---|---|
| 성공으로 보는 조건 | 쿠폰 적용 조건을 충족하고 계산 결과가 규칙에 맞아야 한다. 다만 결과 저장까지 완료해야 성공인지, 예상 금액만 계산해도 성공인지는 미확인이다. |
| 성공 시 보장할 저장 상태 | 미확인 — P-001/Q2의 답이 필요하다. 응답 정보가 정해졌다는 이유만으로 저장 완료를 보장한다고 정하지 않는다. |
| HTTP status | `200 OK` — 성공 결과를 응답 본문으로 전달한다. 성공의 저장 보장 여부는 여전히 미확인이다. |
| meta.result | `SUCCESS` |
| data 유무와 구조 | `data` 객체에 `orderId`·`originalAmount`·`discountAmount`·`finalAmount`를 담는다. |
| 연결할 요구·규칙 | UC-001의 적용 가능 여부 확인·할인 계산·결과 전달 흐름, INV-001~006의 적용 조건과 계산·결과 처리 규칙. 저장 보장 여부는 P-001/Q2와 연결한다. 미확인 정책과 재요청 분기는 관련 질문의 답을 받은 뒤 보완한다. |

아래는 과제에서 요구한 응답 정보에 대해 사용자와 합의한 의미다. 필드명과 주문 ID의 양의 정수 형식은 사용자 검토 후 선택했다. 금액은 설명용 예시만 원 단위를 사용하며 실제 통화·자료형·소수 처리·허용 범위는 미확인이다.

| 응답 정보 | 필드명 | 자료형·단위 | 의미·기준 시점 | 예시 값 | 근거 |
|---|---|---|---|---|---|
| 주문 ID | `orderId` | 양의 정수 | 쿠폰 적용을 요청한 주문의 식별자 | 100 | 과제 지정 응답 정보·사용자 검토 |
| 원금 | `originalAmount` | 미확인 — 예시만 원 단위 | 쿠폰 할인 전 주문 금액 | 10,000원 | 과제 지정 응답 정보·사용자 검토 |
| 할인 금액 | `discountAmount` | 미확인 — 예시만 원 단위 | 이번 적용 결과에서 차감하는 금액 | 1,000원 | 과제 지정 응답 정보·사용자 검토 |
| 최종 금액 | `finalAmount` | 미확인 — 예시만 원 단위 | 원금에서 할인 금액을 뺀 금액 | 9,000원 | A-002·INV-003 |

이 응답을 받았다는 사실만으로 주문이나 할인 금액이 확정됐다고 보지 않는다. 확정 시점과 결과 저장 여부는 P-001/Q1~Q2·P-002/Q1의 답이 미확인이다.

성공 응답 예시 — HTTP `200 OK`:

```json
{
  "meta": {"result": "SUCCESS"},
  "data": {
    "orderId": 100,
    "originalAmount": 10000,
    "discountAmount": 1000,
    "finalAmount": 9000
  }
}
```

금액 10,000 − 1,000 = 9,000은 설명용 값이다. 위 JSON의 숫자 표기로 실제 금액 자료형을 확정하지 않는다. 성공 시 오류 필드의 포함 여부는 미정이며, 예시는 합의한 `meta.result`와 `data`만 보여준다. 적용 조건을 충족한 성공 사례를 가정했으며 결과 저장이나 주문 확정을 보장한다는 뜻은 아니다.

### 오류 계약

실패 응답은 `meta.result: FAIL`, `meta.errorCode`, `meta.message`를 제공하고 `data`는 `null`이다. 다음 표는 각 오류를 단독으로 설명하며, 여러 오류가 동시에 해당할 때의 검사 우선순위는 미정이다.

| 상황·근거 | HTTP · 오류 코드 | 안내 문구 |
|---|---|---|
| 입력 형식 오류 — 입력 설계 | 400 · `INVALID_REQUEST` | 요청 정보를 확인해 주세요. |
| 없는 주문 — 존재 여부 오류 설계 | 404 · `ORDER_NOT_FOUND` | 존재하지 않는 주문입니다. |
| 없는 쿠폰 — 존재 여부 오류 설계 | 404 · `COUPON_NOT_FOUND` | 존재하지 않는 쿠폰입니다. |
| 요청자 소유가 아닌 쿠폰 — P-001·INV-001 | 403 · `COUPON_NOT_APPLICABLE` | 사용할 수 없는 쿠폰입니다. |
| 확정 주문 신규 적용 — P-001 | 409 · `ORDER_ALREADY_CONFIRMED` | 확정된 주문에는 쿠폰을 새로 적용할 수 없습니다. |
| 오류 코드 | 요청자의 다음 행동 | 처리 후 상태 |
|---|---|---|
| `INVALID_REQUEST` | 입력 수정 후 재요청 | 해당 요청의 쿠폰 적용을 수행하지 않는다. |
| `ORDER_NOT_FOUND` | 주문 확인·재선택 | 해당 요청의 쿠폰 적용을 수행하지 않는다. |
| `COUPON_NOT_FOUND` | 쿠폰 확인·재선택 | 해당 요청의 쿠폰 적용을 수행하지 않는다. |
| `COUPON_NOT_APPLICABLE` | 본인이 보유한 쿠폰을 선택해 다시 요청 | 해당 쿠폰을 적용하지 않는다. |
| `ORDER_ALREADY_CONFIRMED` | 해당 주문의 신규 적용 시도를 중단 | 요청한 쿠폰을 새로 적용하지 않는다. |

소유권 오류는 다른 사람의 쿠폰이라는 세부 정보 대신 사용 불가를 알린다. `COUPON_NOT_APPLICABLE`을 만료·교체 등 미확인 상황에도 사용한다고 정하지 않는다. 이미 성공한 요청의 재전송을 신규 적용 오류로 간주하지 않는다.

공통 실패 구조의 대표 예시 — HTTP `400`:

```json
{
  "meta": {
    "result": "FAIL",
    "errorCode": "INVALID_REQUEST",
    "message": "요청 정보를 확인해 주세요."
  },
  "data": null
}
```

### 아직 확정할 수 없는 처리

| 상황 | 확인된 부분 | 미확인 처리·관련 질문 |
|---|---|---|
| 만료 시각을 지난 쿠폰 요청 | 요청 시작 시각을 기준으로 만료 판단 | 요청 처리·응답·후속 상태 — A-004/Q2 |
| 확정 전 A가 적용된 주문에 B 요청 | 두 장 동시 적용 불가 | 교체 또는 거절·기존 금액 처리 — P-001/Q3 |
| 같은 요청 재전송 | A-003·INV-005의 결과 재사용 | 같은 요청 기준·실패 포함 여부·조건 충돌 우선순위 |

만료 시각과 요청 시작 시각이 같은 순간은 A-004/Q1의 미확인 사항이다. 금액·저장 시점 등 미확인 정책도 응답 예시로 확정하지 않는다.

### 재요청과 조건 충돌

| 항목 | 작성 내용 |
|---|---|
| 같은 요청을 구분할 기준과 근거 | 미확인 — A-003/Q1. 주문 ID와 쿠폰 ID가 같다는 이유만으로 같은 요청이라고 정하지 않는다. |
| 재요청 시 반환할 결과 | A-003·INV-005에 따라 같은 요청의 결과를 재사용한다. 실패 결과도 재사용하는지는 A-003/Q2의 미확인 사항이다. |
| 재요청과 다른 조건이 겹칠 때의 판단 | 할인 정책이 바뀐 경우는 A-003/Q3에 연결한다. 쿠폰 만료·주문 확정 후의 재요청은 [규칙 문서의 충돌 검토](invariants.md)에 연결하며 처리 우선순위는 미확인이다. |
| 관련 제품 질문과 답변 상태 | A-003/Q1~Q3 및 기존 만료·주문 확정 후 재요청 충돌 검토 질문. 정책 답변은 미확인이다. |

설명용으로 처음 결과가 할인 금액 1,000원·최종 금액 9,000원이었다면, 같은 요청으로 판단되고 결과 재사용 대상이라면 그 결과를 다시 반환한다. 이 예시로 같은 요청의 기준이나 재사용 대상을 확정하지 않는다.

### 기본 형태와의 차이

현재 합의한 method·path·요청 필드·성공 응답 정보는 과제 지정 형태와 차이가 없다. `POST /api/v1/orders/{orderId}/discount`를 유지한다. 금액 표현과 정수 상한 등 미확정 항목은 별도로 남긴다.

선택 이유: 과제에서 지정한 API 형태를 사용한다. 상태 코드의 일반적인 의미는 [HTTP 표준 RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-15)에 근거하며, 각 오류에 상태 코드를 연결한 것은 사용자와 선택한 설계다. 실제 API 관찰 결과가 아니다.

**상세 참고:** [API 계약과 전체 응답 예시](api-contract.md)

## 8. 책임과 설계 결정

처리 순서는 서비스가 조정하고 세부 판단은 각 책임에 맡긴다. 이 구분이 반드시 별도 클래스를 뜻하지는 않는다. 세 결정은 제품 정책의 답이 아니라 학습자가 선택한 설계다.

### 책임별 보장

| 책임 | 담당 후보 | 보장할 상태·행동 | 선택 이유 | 관련 요구·규칙 | 미확인 사항 |
|---|---|---|---|---|---|
| 처리 순서 조정 | 쿠폰 적용을 진행하는 서비스 | 조회·검증·계산·필요한 저장을 조정한다. | 호출자가 내부 처리 순서를 일일이 알 필요가 없도록 한다. | UC-001·DEC-003 | 저장 시점과 재요청 처리 우선순위 |
| 주문 상태 확인 | 주문 상태를 판단하는 부분 | 확정된 주문의 신규 적용을 막는다. | 주문 상태에 따른 적용 제한을 담당한다. | P-001 | 주문 확정 시점과 확정 후 재요청 처리 |
| 쿠폰 사용 가능 여부 확인 | 쿠폰 조건을 판단하는 부분 | 보유자를 확인하고 요청 시작 시각으로 만료 여부를 판단한다. | 쿠폰 사용 조건의 판단을 담당한다. | INV-001·INV-006 | 만료 시각과 같은 순간의 판단·만료 시 처리 |
| 할인 계산 | 금액을 계산하는 부분 | 최종 금액 = 원금 − 할인 금액을 보장한다. | 금액 관계를 담당한다. | INV-003 | 금액 허용 범위 |
| 결과 저장 | 할인 결과를 저장·조회하는 부분 | 확정된 할인 결과를 보존하고 다시 읽을 수 있게 한다. | 확정된 결과를 유지한다. | INV-004·DEC-002 | 할인 확정 시점과 확정 전 저장 여부 |

서비스는 전체 작업의 진행 담당자다. 세부 판단은 각 책임에 맡기며, 각 부분을 반드시 별도 클래스로 만든다는 뜻은 아니다.

### DEC-001. 오류 구분과 표현

| 비교할 대안 | 호출자에게 주는 정보 | 장점 | 비용·한계 |
|---|---|---|---|
| 오류 코드와 안내 문구 함께 제공 | 프로그램의 오류 구분 기준과 사람이 읽을 설명 | 안내 문구가 바뀌어도 오류 구분 기준을 유지할 수 있다. | 코드별 의미를 정리하고, 같은 코드를 다른 의미로 바꾸지 않도록 관리해야 한다. |
| 안내 문구만 제공 | 사람이 읽을 설명 | 별도 오류 코드 목록 없이 사람이 읽을 설명을 제공할 수 있다. | 문구를 오류 구분 기준으로 사용하면 문구 변경이 화면 처리에 영향을 줄 수 있다. |

| 결정 항목 | 작성 내용 |
|---|---|
| 선택 방식 | 프로그램이 구분할 오류 코드와 사람이 읽을 안내 문구를 함께 제공한다. 쿠폰 소유권 오류와 주문 확정 오류는 서로 다른 코드로 구분한다. |
| 버린 대안 | 안내 문구만 제공하는 방식 |
| 선택 이유 | 문구가 바뀌어도 화면에서 오류 종류를 구분하는 기준은 유지할 수 있기 때문이다. |
| 관련 요구·규칙 | P-001·INV-001 및 API 계약의 쿠폰 소유권 오류·확정된 주문의 신규 적용 오류 |
| 미확인 사항 | 쿠폰 소유권 오류는 `COUPON_NOT_APPLICABLE`, 확정된 주문의 신규 적용 오류는 `ORDER_ALREADY_CONFIRMED`로 정했다. HTTP 상태 코드는 각각 `403 Forbidden`과 `409 Conflict`로 정했다. 제품 정책의 답이 필요한 오류는 기존 미확인 상태를 유지한다. |

예를 들어 “사용할 수 없는 쿠폰입니다.”를 “이 쿠폰은 사용할 수 없어요.”로 바꿔도 오류 코드가 같으면 화면의 오류 처리 방식을 유지할 수 있다. 이 결정은 사용자 검토 후 선택한 설계이며 제품 정책의 답변이 아니다.

추가로 입력 형식 오류는 `400 / INVALID_REQUEST`, 없는 주문은 `404 / ORDER_NOT_FOUND`, 없는 쿠폰은 `404 / COUPON_NOT_FOUND`로 구분한다. 모두 학습자가 선택한 오류 설계이며 `FAIL`, 안내 문구, `data: null`을 제공한다. 구체적인 예시와 다음 행동은 [API 계약](api-contract.md)에 기록한다. 동시에 여러 오류가 해당하는 경우의 검사 우선순위는 미정이다.

### DEC-002. snapshot 저장과 재계산

snapshot은 특정 시점의 결과를 기록해 두는 방식을 뜻한다. 두 방식의 적합성은 관련 약속과 규칙을 근거로 비교한다.

| 비교할 대안 | 필요한 데이터 | 장점 | 비용·한계 |
|---|---|---|---|
| snapshot 저장 | 확정된 할인 결과. 세부 저장 항목은 미작성 | 정책이 바뀌어도 기록한 확정 금액을 사용할 수 있다. | 확정 결과를 저장할 공간과 저장·조회 처리가 필요하다. |
| 현재 정책으로 재계산 | 현재 쿠폰 정책과 계산에 필요한 정보 | 조회 시점의 정책을 반영한 금액을 구할 수 있다. | 현재 정책으로 다시 계산하면 확정된 할인 금액이 달라질 수 있어 확정 금액 보존에는 적합하지 않다. |

| 결정 항목 | 작성 내용 |
|---|---|
| 선택 방식 | 확정된 할인 결과를 기록해 두고 사용하는 snapshot 저장 |
| 버린 대안 | 조회할 때마다 현재 쿠폰 정책으로 다시 계산하는 방식 |
| 선택 이유 | 정책이 바뀌어도 확정된 할인 금액을 유지해야 하기 때문이다. |
| 관련 요구·규칙 | P-002·INV-004 |
| 미확인 사항 | 할인 금액이 확정되는 시점(P-002/Q1)과 확정 전 결과의 저장 여부(P-001/Q2) |

할인 금액이 1,000원으로 확정됐다면 이후 쿠폰 할인율이 바뀌어도 기록한 1,000원을 사용한다. 이 결정은 확정된 결과의 보존 방식이며, 쿠폰 적용 요청을 받자마자 저장한다고 정한 것은 아니다.

### DEC-003. 처리 순서를 조정하는 내부 경계

주문·쿠폰 조회부터 할인 계산·저장까지의 호출 순서를 어느 내부 경계가 조정하고 숨길지 비교한다.

| 비교할 대안 | 순서를 조정할 곳 | 호출자가 알아야 할 내용 | 장점 | 비용·한계 |
|---|---|---|---|---|
| 서버 내부 서비스가 조정 | 쿠폰 적용을 진행하는 서비스 | 쿠폰 적용 요청과 결과를 받는 방법 | 호출자가 내부 처리 순서를 알 필요가 없다. | 모든 판단을 서비스에 몰아넣지 않고 세부 판단을 각 책임에 맡겨야 한다. |
| 화면이 각 단계를 호출 | 화면 | 조회·검증·계산·저장의 호출 방법과 순서 | 화면에서 각 단계의 호출 순서를 직접 제어할 수 있다. | 내부 순서가 바뀌면 화면도 수정해야 하고 단계가 빠질 수 있다. 이번 설계에서는 내부 절차를 화면이 알아야 하는 부담 때문에 선택하지 않는다. |

| 결정 항목 | 작성 내용 |
|---|---|
| 선택 방식 | 서버 내부의 쿠폰 적용 서비스가 처리 순서를 조정한다. |
| 버린 대안 | 화면이 조회·검증·계산·저장을 각각 호출하며 순서를 관리하는 방식 |
| 선택 이유 | 호출자가 내부 처리 순서를 일일이 알 필요 없이 쿠폰 적용을 요청하고 결과를 받을 수 있다. |
| 관련 요구·규칙 | UC-001·INV-001~006 및 위 책임별 보장 |
| 미확인 사항 | 저장 시점과 재요청·만료·주문 확정 조건의 처리 우선순위. 이 결정으로 구체적인 실행 순서를 확정하지 않는다. |

### 외부 약속과 내부 변경 검토

| 검토할 변경 | 유지해야 할 외부 약속 | 내부에서 바뀔 부분 | 호출자 수정 여부·근거 | 관련 결정 |
|---|---|---|---|---|
| 오류 안내 문구 변경 | 오류 코드와 의미 유지 | 안내 문구 | 코드로 분기하는 호출자의 처리 로직은 수정할 필요가 없다. | DEC-001 |
| snapshot 저장 위치 변경 | 확정 금액과 응답 계약 유지 | 확정 결과의 저장 위치 | 호출자는 수정할 필요가 없다. | DEC-002·DEC-003 |
| 내부 조회 순서 변경 | 적용 규칙과 응답 계약 유지 | 서비스 내부 조회 순서 | 호출자는 수정할 필요가 없다. 재요청 결과가 달라진다면 외부 약속 유지 조건을 충족하지 못한다. | DEC-003·INV-005 |

## 10. 미확인 사항과 문서 검토

합의한 설계를 한 문서에 통합한 상태다. 아래 미확인 정책과 미정 설계가 남아 있어 구현자가 임의로 답을 채워서는 안 된다.

| 남은 항목 | 현재 상태와 영향 |
|---|---|
| 제품 질문 17개와 충돌 질문 | 정책 답 미확인. 3절의 영향과 6절의 범위 확인 필요 |
| 성공·결과 저장·확정 시점 | 예상 결과인지 저장 완료인지 미확인. snapshot 선택만으로 저장 시점을 정하지 않음 |
| 금액 표현과 계산 | 실제 통화·자료형·소수 처리·허용 범위 미확인. 할인율·정액 등 계산 기준도 미확인 |
| 요청자 식별의 구체 방식 | 검증된 로그인 정보 사용은 설계 선택. 세션·토큰 등 인증 방식과 그 밖의 호출 권한은 미정 |
| 요청 기준·검사 순서 | 같은 요청 식별 기준과 재사용 범위 미확인. 만료·확정·다중 오류의 검사 우선순위 미정 |
| 세부 구현 정보 | 정수 상한·snapshot 세부 저장 항목·구체 클래스·저장 위치 미정 |
| 성공 응답 오류 필드 | 성공 시 오류 필드 포함 여부 미정. 예시는 합의한 필드만 표시 |
| 추가 범위·제약 | 분할 문서의 추가 범위 작성란은 미작성. 이 통합으로 새 범위를 확정하지 않음 |

분할 문서는 당시 학습 기록을 그대로 유지했다. 식별 형식·snapshot 등 후속 결정이 반영되기 전의 미작성 표시가 일부 남아 있으며, 이 문서는 API 계약·DEC의 후속 합의를 연결해 현재 상태로 정리했다.
