# R03 회복 전략·통합 검증 요구사항

## 상태·목표

- 상태: **구현 전**. [R02](../r02-pg-order-payment/requirement.md) 병합 후 시작한다.
- 최신 `volume-5/main`에서 `volume-5/r03-payment-resilience`를 생성한다. PR 대상은 `volume-5/main`이다.
- 기존 거래 조회의 호출·대기 한도를 정하고 회로 차단·fallback·복구를 검증한다. 통합 장애 실험과 제출 자료를 정리한다.

상위 기준은 [전체 요구사항](../total_requirement.md), 회복 요구는 [Implementation Quest](../reference/implementation-quest.md)다.

## 회복 전략

- 실제 HTTP timeout과 create 재시도 차단은 R01부터 적용한다. 이 PR에서 새로 시작하는 항목으로 미루지 않는다.
- retry를 추가하면 기존 거래 조회에만 적용한다. 횟수·간격·총 예산을 제한하고 실제 lookup 횟수를 확인한다.
- PG 조회 한 경로에 circuit breaker를 적용하고 최소 표본·실패/지연 조건·OPEN 대기·HALF_OPEN 탐색 호출 수를 정한다.
- 업무 거절과 네트워크/조회 장애를 회로의 실패 표본에서 어떻게 구분할지 정한다.
- 조회 실패·회로 차단의 fallback은 저장된 상태와 확인 불가를 반환한다. 가짜 성공·확정 실패·포인트 대체·임의 재고 복구를 만들지 않는다.
- 회로 OPEN이 이미 발송한 시도를 미발송으로 되돌리지 않으며, 회복 뒤 기존 거래 조회를 재개한다.
- client·retry·circuit breaker 중첩에서 실제 호출 수와 실패 표본 단위를 확인한다. bulkhead·상시 스케줄러는 필수로 추가하지 않는다.
- 라이브러리·버전·설정값·decorator/AOP 방식은 설계에서 정하며 설치돼 있다고 가정하지 않는다.

## 통합 장애·기존 기능·제출

- R01/R02의 개별 검증을 전제로 외부 거래·DB·controller가 연결된 장애 순서를 결정적으로 재현한다.
- PG 성공 후 내부 commit 실패, 발송 기록 후 프로세스 재생성, callback/대사 동시 적용과 늦은 응답을 검증한다.
- 외부 거래 수·create/lookup 횟수·주문/시도/차감 처리 상태·가용 재고·포인트를 함께 확인한다.
- 과거 POINT 기록·품목·금액, 포인트 충전/조회, 재고 부족/삭제의 PG 미호출을 보존한다.
- 차감 후 삭제 상품의 종결·실패 복구, 관리자 가용 재고 설정의 경쟁, 차감/복구의 캐시 commit/rollback을 확인한다.
- 실제 코드에 연결한 실행 경로·설정·관측 방법과 장기 미확인·자동 완료 한계를 문서에 남긴다.
- 기술 글은 실제 요청/실패 장면, 핵심 개념, 선택 이유·이득·비용·해결하지 못한 상황을 설명한다.

## 완료 조건·대표 검증

- [ ] 실제 HTTP timeout·총 대기·lookup 횟수가 제한되고 create 자동 재시도가 없다.
- [ ] CLOSED → OPEN → HALF_OPEN → CLOSED 또는 재차단을 통제한 순서로 확인한다.
- [ ] OPEN 중 실제 외부 조회가 차단돼도 미완료 결제·차감 재고가 유지되고 회복 후 같은 거래 조회가 재개된다.
- [ ] 응답 유실·내부 저장 실패·재시작·동시 결과 적용에서 추가 외부 거래나 중복 확정/복구가 없다.
- [ ] 0건·복수 거래·식별/금액 불일치·충돌에서 임의 종결·재결제·재고 복구가 없다.
- [ ] 기존 기능·결정된 사용자 경계·캐시 회귀와 전체 check의 실제 실행 건수·실패·skip·종료 결과를 확인한다.
- [ ] 서버·worker·실험 자원을 정리하고 상태/트랜잭션 설계·실제 결과·기술 글을 작성한다.
- [ ] PR 설명에 대표 효과 수와 미확인 처리 한계를 기록한다. 원격 PR 생성·게시 시점은 실제 후속 작업에서 정한다.
