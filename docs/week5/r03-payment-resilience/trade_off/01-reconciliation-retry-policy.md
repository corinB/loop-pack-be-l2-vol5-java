# 자동 재확인·실패 분류·수동 전환

[전체 설계 질문](total_trade_off.md) · [요구사항](../requirement.md) · [R01 모델 논의](../../r01-pg-payment-foundation/trade_off/01-payment-attempt-ownership.md)

상태: **재조회 정책·실행 방향 확정·세부 설계 전·구현 전**.

## 사용자 결정과 남은 질문

2026-10-21 사용자는 기존 거래를 자동으로 다시 확인하는 방식을 선택했다.
이어 최초 조회 후 추가 재시도 최대 3회, 간격 1초·3초·10초, 지터 ±20%와 아래 실패/수동 전환 기준을 확정했다.
원문의 수동 reconcile 기본 경로에 자동 재확인을 추가하는 사용자 결정이며 원문 파일은 변경하지 않는다.

- 확정: 최초 조회 1회와 추가 재조회 최대 3회, 앞선 확인 종료 후 1초·3초·10초 대기와 각 간격의 지터 ±20%.
- 확정: 아래 분류에 따라 확정 실패는 실패 반영, 일시적 조회 장애/처리 중/빈 조회는 한도 내 재확인, 충돌/설정 오류 등은 즉시 수동 전환한다.
- 확정: 수동 전환은 자동 작업 중단이며 결제 실패가 아니다. 수동 대사와 늦은 callback도 같은 검증·멱등 반영 경계를 사용한다.
- 확정: 정상 실행은 @Retryable로 처리하고 DB에 진행을 저장한다. 후속 결정으로 서버 장애 뒤 자동 재개는 담당자 수동 대사로 변경했다. [실행 방식 결정](06-reconciliation-execution.md)을 따른다.
- 확정: 조회 작업 직전에 사용 횟수를 DB에 기록하고 commit한다. 기록 뒤 HTTP 전에 종료돼도 해당 회차는 소비한 것으로 유지한다. [횟수 기록 결정](07-retry-attempt-accounting.md)을 따른다.
- 후속 확정: R01 [HTTP 설정](../../r01-pg-payment-foundation/trade_off/03-http-client-settings.md)은 연결 1초·연결 풀 대기 1초·응답 대기 2초와 client 자동 retry/redirect 차단이다. [adapter](../../r01-pg-payment-foundation/trade_off/04-adapter-fixture.md)는 관찰/확인 불가 사유를 결과값으로 반환하며 재조회 제어와 회로는 결과 분류에 연결한다.
- 미정: 전체 작업 시간 예산, 구체적인 관찰/재조회 예외 매핑, 회로 OPEN·callback·수동 조회의 계수 규칙.
- 미정: 저장 필드·조회 작업과 실제 HTTP 호출의 관계·횟수 기록의 원자성/동시 실행 조율·프록시/실행기 구성, 내부 결과 반영 재시도 예산.
- 정책 확정은 구현·검증 완료를 뜻하지 않는다. 상태 enum·테이블·구체적인 의존성 버전은 아직 정하지 않았다.

## 이미 정해진 안전 조건

- 발송 시작 기록 뒤 PG 결제 생성은 자동 재시도하지 않는다. 응답 유실·서버 오류·재시작도 예외로 삼지 않는다.
- 결제 실패로 종결할 근거는 검증한 PG FAILED 또는 계약에 정확히 맞는 거래 생성 전 확정 거절이다.
- 확정 거절은 HTTP 422, TEST_PG_REJECTED_BEFORE_CREATE, transactionCreated=false, 일치하는 orderId/amount를 함께 검증한다.
- 시간 경과·조회 실패·조회 0건/404·재시도 소진·회로 OPEN은 결제 실패의 근거가 아니다.
- 확정 실패에 따른 재고 복구와 주문/시도 변경은 같은 로컬 TX에서 한 번만 적용한다.
- PG 결과가 확인됐더라도 내부 반영 TX가 실패하면 적용 완료로 기록하지 않는다. 이미 확인한 결제 사실도 반대로 바꾸지 않는다.

## 확정한 실패 분류·처리 기준

| 관찰한 상황 | 처리 | 결제·재고 의미 |
|---|---|---|
| 최초 검증·재고 부족·삭제 등 TX A 실패 | 요청 거절·전체 rollback, PG 미호출 | 결제 실패 거래를 만들지 않으며 차감도 남기지 않음 |
| 검증된 PG FAILED / 거래 생성 전 확정 거절 | 실패 결과를 한 번 반영 | 반영 TX commit 시 재고 한 번 복구 |
| 생성 응답 timeout·유실·불완전 응답·일반 오류 | 기존 거래 조회를 예약 | 결과 미확인, 차감 유지·create 금지 |
| 조회 통신 장애·일시적 서버 오류 | 예산 내 재조회, 소진 시 수동 전환 | 마지막 확인 사실 유지, 차감 유지 |
| 조회 PENDING·0건·404 | 예산 내 나중에 다시 조회, 소진 시 수동 전환 | PENDING은 처리 중이며 실패 아님. 빈 조회도 재발송/복구 근거 아님 |
| 복수 거래·주문/금액/계정 불일치·종결 충돌 | 즉시 수동 확인으로 전환 | 충돌 사실 보존, 기존 종결 상태 보호·임의 복구 금지 |
| 조회 인증/설정 오류·반복이 도움이 안 되는 계약 오류 | 즉시 수동 확인으로 전환 | 설정/계약 수정 전 자동 반복 중단, 결제 실패로 변환하지 않음 |
| 검증된 결과의 내부 반영 중 확실히 rollback된 일시적 DB 오류 | 같은 결과 적용을 제한적으로 재수행, 소진 시 수동 전환 | PG 재결제 금지, 로컬 반영 성공 전 완료 처리 금지 |
| 내부 반영의 영구적 업무 충돌·무결성 문제 | 즉시 수동 확인으로 전환 | PG 결과와 내부 미반영을 함께 보존, 새 결제/임의 재고 복구 금지 |

DB commit 결과가 불명확하면 저장 상태를 먼저 확인하고 공통 멱등 반영 경계를 사용한다.
유일 제약 충돌은 기존 시도·저장 결과를 확인할 경로이며, 모든 DB 예외를 일시적 오류로 묶어 재시도하지 않는다.
관찰 검증은 R01 adapter 경계, 재조회/최종 반영 판단은 application과 도메인에 둔다. 구체적인 필드별 HTTP/사유 코드·재조회 예외 매핑은 아직 미정이다.

## 확정한 횟수·간격과 비용

- 최초 확인 뒤 추가 재조회 최대 3회로 조회 작업은 최대 4회다. 중간에 반영 완료하거나 즉시 수동 전환 사유가 확인되면 남은 재조회를 중단한다.
- 앞선 확인 종료 뒤 1초·3초·10초를 대기하며 각 대기에 지터 ±20%를 적용한다. 각 대기의 범위는 0.8~1.2초·2.4~3.6초·8~12초다.
- 세 대기 시간의 합은 11.2~16.8초다. HTTP 실행·DB 반영·스케줄링 지연이 추가되므로 전체 완료 시간이 이 범위라는 뜻은 아니다.
- 짧은 간격은 빠른 회복에 유리하지만, PG 처리 시간이 길면 매번 PENDING만 보고 수동으로 넘기게 된다.
- 긴 간격은 같은 횟수로 더 긴 처리 지연을 관찰하지만 재고 확보·고객 대기도 길어진다.
- 지터는 여러 시도의 재조회 시점을 흩뜨리며, 장애 해결이나 개별 호출 timeout을 대신하지 않는다.
- PG 학습 시나리오의 완료 시간과 재확인 창을 함께 정한다. 최대 4회의 조회 작업 안에 모든 거래가 완료될 보장은 없다.
- 한 회의 복구 작업이 주문별 거래 목록 조회와 개별 거래 조회를 함께 요구할 수 있다. 작업 회수와 실제 HTTP 호출 수를 구분한다.
- 자동 작업의 최초+추가 3회 외에 HTTP client/library retry가 중첩돼 실제 호출을 늘리지 않도록 구성한다. 실제 HTTP 호출 예산은 조회 흐름과 함께 확정한다.
- 프로세스 재시작으로 횟수를 초기화하지 않는다. 조회 직전 commit한 회차는 사용한 것으로 유지한다. 회로 OPEN의 예산 처리와 callback/수동 조회 계수는 후속 설계에서 정한다.

## 확정한 수동 전환의 의미

수동 전환은 자동 작업을 멈추고 확인이 필요한 대상으로 남기는 것이다. 결제의 최종 실패 상태가 아니다.
미확인이면 재고를 유지하고, 실패는 확인했지만 복구 TX가 실패했다면 미반영 사실을 남겨 같은 복구를 마무리한다.
수동 reconcile은 저장된 검증 종결 결과의 재적용 또는 PG 권위 조회·식별 검증·관찰 저장 뒤 공통 업무 반영을 사용한다. 운영자 입력만으로 성공/실패/재고를 강제 변경하지 않는다. 특히 거래 없는 확정 거절은 먼저 저장한 근거로 재적용한다.
수동 전환 뒤에도 늦은 callback의 검증된 결과를 받아 마무리할 수 있으며 충돌 보존과 종결 상태 보호를 유지한다.
수동 대사의 호출 예산·정상 실행과의 경합·사유/마지막 오류·미확인 기간 표시·정확한 상태 표현은 후속 설계 질문이다. 장애 중단 자동 작업을 재시작 시 재개하는 안은 담당자 수동 대사로 대체됐다.
후속 [최소 보완](../../r01-pg-payment-foundation/trade_off/10-learning-scope-completion.md)에서 수동 실행 ID 교체·옛 진행 갱신 차단과 관찰 저장/업무 TX 분리를 확정했다. commerce 지터/다음 실행 예약 정보는 DB에 보존하지 않는다. 정확한 조건식·응답/예산은 후속 설계 대상이다.

## PR 책임

- R01: 결과·관찰 오류·복구 진행을 표현할 모델 경계와 저장 요구를 먼저 설계한다. 구체적인 필드·상태는 미정이다.
- R02: 기존 거래 조회·공통 결과 적용·수동 reconcile을 연결하고 한 번만 적용되는 업무 효과를 검증한다.
- R03: 자동 재확인 실행·제한/지터·수동 전환·회로와의 결합을 구현하고 재시작/장애 실험으로 확인한다.

현재 실행 방향은 [@Retryable + DB 진행 기록 + 중단 시 운영 담당자 수동 대사](06-reconciliation-execution.md)다. 이전 재시작 자동 재개는 이 후속 결정으로 대체했다.
HTTP client·하위 timeout 초기값·결과값 반환 방향은 위 R01 후속 결정을 따른다. 구체적인 의존성 버전·테이블·전체 실행 예산은 아직 선택하지 않았다. 기능 구현·테스트 완료를 의미하지 않는다.
