# 학습용 PG의 독립 실행·거래 저장

[전체 설계 질문](total_trade_off.md) · [요구사항](../requirement.md)

## 판단할 문제

사용자는 학습용 PG를 직접 만들고 commerce가 실제 HTTP로 연결하는 구성을 요구했다.
테스트 클래스 안에서만 실행되는 HTTP fixture를 넘어, 로컬에서 별도로 실행할 수 있는 작은 서버가 필요하다.
PG 거래 저장 방식은 사용자가 메모리 선택을 철회하고 DB 저장으로 변경했다.

> **확정 — 독립 실행 테스트 PG·기존 MySQL의 PG 전용 스키마에 거래 저장**
>
> 2026-10-21 사용자 최종 선택이다. 메모리 저장은 채택안이 아니다.
> PG 재시작 뒤에도 거래·결과를 같은 키로 조회한다. 실제 카드·금전·외부 PG 계정은 사용하지 않는다.
> DB 배치는 기존 MySQL 서버 안에 commerce와 구분되는 PG 전용 스키마를 두는 것으로 사용자와 확정했다.

## 저장 방식 비교

| 기준 | DB 저장 · 채택 | 메모리 저장 · 철회 |
|---|---|---|
| 실행 중 생성·조회 | DB에서 거래를 저장·조회 | 프로세스 메모리에서 저장·조회 |
| PG 재시작 | 저장된 거래를 다시 조회 | 거래 초기화 |
| 복구 실험 | commerce와 PG의 재시작을 구분해 검증 가능 | PG를 켜 둔 채 commerce 재시작을 검증 |
| 추가 구성 | DB 연결·테이블·스키마 반영·테스트 데이터 정리 필요 | 저장 구조가 간단함 |

## DB 배치 결정

| 기준 | 기존 MySQL의 PG 전용 스키마 · 채택 | 별도 MySQL 인스턴스 · 미채택 |
|---|---|---|
| 실행 구성 | 기존 서버를 재사용하고 스키마·접근 설정을 분리 | 서버·포트·볼륨 설정 추가 |
| 데이터 경계 | commerce와 PG의 스키마를 구분 | 서버와 스키마를 구분 |
| DB 장애 | MySQL 서버 장애는 두 앱에 함께 영향 | DB 인스턴스별 장애 실험 가능 |
| 이번 선택 | 학습용 기존 인프라를 재사용한다는 사용자 결정 | 이번 구성에서는 추가하지 않음 |

스키마 이름·계정/권한·테이블과 초기화 방식은 아직 정하지 않았다.
같은 MySQL을 사용해도 두 앱은 자기 스키마를 대상으로 동작하고 업무 연동은 HTTP를 사용한다.

## 다음 논의 · 실패 시나리오 제어

아래는 비교할 후보이며 채택 전이다. 무작위 성공/실패보다 동일한 실패 순서를 재현할 수 있는 구성을 우선한다.

| 기준 | 기동 설정으로 공통 모드 지정 | PG 전용 제어 API로 주문별 지정 · 제안 |
|---|---|---|
| 사용 | 설정·기동 옵션으로 성공/실패/지연 모드를 고정 | 결제 전에 주문 ID별 시나리오를 지정 |
| 장점 | 제어용 endpoint가 적고 초기 구성이 단순 | 주문별 재현과 여러 요청의 서로 다른 실패 순서 제어가 쉬움 |
| 비용 | 모드 변경에 설정 변경이 필요하고 공통 모드는 동시 실험에 제약 | 테스트용 API·시나리오 조회/초기화 범위 설계 필요 |
| 원문 결제 계약 | 생성/조회 계약 유지 | 생성/조회 계약을 유지하고 PG 쪽 테스트 제어 경로를 구분 |

예시는 주문 A의 성공, 주문 B의 확정 실패, 주문 C의 거래 생성 뒤 응답 유실이다.
제어 API 채택 여부·시나리오 종류·상태 전이 시점·callback 발생 조건은 사용자와 논의 후 정한다.

## 구현으로 이어질 요구

- PG 생성·거래 조회·주문별 조회의 원문 HTTP 계약을 유지한다.
- 같은 orderId의 새 POST를 자동 중복 제거하지 않는다. 호출·거래 수와 결과 상태를 관찰할 수 있어야 한다.
- 성공·실패·처리 중·지연·거래 생성 뒤 응답 유실을 학습에 맞게 통제한다.
- PG의 거래 DB와 commerce의 시도/주문 DB를 서로 다른 사실의 원본으로 다룬다. 직접 조인·공유 TX로 HTTP 경계를 우회하지 않는다.
- PG 재기동 때 거래를 초기화하지 않는다. 의도적인 테스트 데이터 정리와 평상시 기동을 구분한다.
- R01에서는 테스트 PG와 실제 commerce adapter의 연결을 검증하고, 주문 confirm·callback 수신 연결은 R02에서 검증한다.

## 남은 설계 질문

- 독립 실행 모듈·명령·로컬 포트와 실행 방법.
- 확정한 기존 MySQL의 PG 전용 스키마 이름·계정/권한·접근 설정.
- 스키마 반영·초기화·테스트 정리 방식. 기존 commerce의 local/test `ddl-auto: create`를 무심코 재사용하지 않도록 검토한다.
- 결과 전이·시나리오 제어·callback 발송 방식과 PG 재시작 시 미완료 거래를 다루는 범위.

독립 실행·DB 저장·기존 MySQL의 PG 전용 스키마 분리는 확정했고 나머지 세부 구현은 아직 결정하지 않았다.
이 문서는 기능 구현·테스트 통과를 의미하지 않는다.
